# 1. 컴퓨터 성능의 이해와 측정 (Slides 3-24)

## 성능의 정의와 영향 요소 (Slides 3-5)

### Slide 3: 성능(Performances) 단원의 개요

이번 장에서는 컴퓨터 구조의 핵심 지표인 '성능'에 대해 학습합니다. 강의 자료에 명시된 것처럼, 이 내용은 세계적으로 널리 쓰이는 컴퓨터 구조 교과서인 *Computer Organization and Design (COD)*의 1.6장 내용을 바탕으로 구성되었습니다.

우리가 컴퓨터를 설계하거나 구매할 때 가장 중요하게 고려하는 기준은 결국 "이 컴퓨터가 얼마나 빠른가?" 혹은 "얼마나 많은 일을 처리할 수 있는가?"입니다. 하지만 성능은 단순히 하나의 숫자로만 정의되지 않습니다. 이 단원에서는 성능을 결정짓는 다양한 하드웨어적, 소프트웨어적 요인을 분석하고, 이를 수식으로 정의하여 객관적으로 비교하는 방법을 배울 것입니다. 컴퓨터 구조론의 관점에서 성능을 이해하는 것은 하드웨어 설계자가 효율적인 프로세서를 만들기 위한 기초이자, 소프트웨어 개발자가 하드웨어 자원을 최적으로 활용하는 코드를 작성하기 위한 필수 지식입니다.

### Slide 4: 성능을 결정하는 4가지 핵심 요소

컴퓨터의 성능은 단순히 CPU의 클럭 속도에만 의존하지 않습니다. 프로그램이 실행되어 결과를 내기까지의 전체 과정에는 여러 계층의 요소들이 관여하며, 각 요소는 성능의 서로 다른 측면을 결정합니다.

1.  **알고리즘(Algorithm):** 소프트웨어의 논리 구조를 결정합니다. 알고리즘은 프로그램이 특정 작업을 완료하기 위해 수행해야 하는 '연산의 총 횟수'를 결정합니다. 예를 들어, 효율적인 정렬 알고리즘은 그렇지 않은 알고리즘보다 훨씬 적은 수의 비교 연산만으로 작업을 끝낼 수 있습니다.
2.  **프로그래밍 언어, 컴파일러, 아키텍처(Programming language, compiler, architecture):** 작성된 코드가 실제 기계어로 번역되는 효율성을 결정합니다. 컴파일러와 명령어 집합 구조(ISA)는 '연산 하나당 실행되는 기계어 명령어의 개수'에 영향을 미칩니다. 같은 논리라도 아키텍처에 따라 더 적은 명령어로 구현될 수 있습니다.
3.  **프로세서와 메모리 시스템(Processor and memory system):** 하드웨어의 물리적인 실행 속도를 결정합니다. CPU가 초당 몇 개의 사이클을 돌리는지, 그리고 메모리에서 데이터를 얼마나 빨리 가져오는지에 따라 '명령어가 실행되는 속도'가 달라집니다.
4.  **입출력 시스템과 운영체제(I/O system including OS):** 외부 장치와의 상통 성능을 결정합니다. 디스크 읽기/쓰기나 네트워크 통신과 같은 I/O 작업이 얼마나 빨리 수행되는지는 운영체제의 스케줄링 능력과 하드웨어 인터페이스 속도에 좌우됩니다.

결론적으로 성능 향상을 위해서는 이 4가지 계층이 모두 조화롭게 최적화되어야 합니다.

### Slide 5: 성능 정의의 상대성 (비행기 사례를 통한 이해)

성능을 정의할 때 가장 먼저 마주하는 문제는 "무엇을 기준으로 삼을 것인가?"입니다. 슬라이드에 제시된 비행기 비교 차트는 성능 지표의 다양성을 명확하게 보여줍니다.

- **여객 수송 용량(Passenger capacity):** 한 번에 얼마나 많은 사람을 태울 수 있는가? 이 기준으로는 **Airbus A380-800**이 압도적입니다.
- **운항 거리(Cruising range):** 얼마나 멀리 갈 수 있는가? 이 기준에서는 **Boeing 777-200LR**이 가장 뛰어납니다.
- **비행 속도(Cruising speed):** 얼마나 빨리 도착하는가? 이 지표에서는 초음속 여객기인 **BAC/Sud Concorde**가 최고의 성능을 가집니다.
- **수송 효율(Passenger throughput):** 단위 시간당 몇 명을 얼마나 멀리 보낼 수 있는가? 즉, $\text{승객 수} \times \text{속도}$의 개념입니다. 이 관점에서는 다시 **Airbus A380-800**이 우위를 점합니다.

이 비유를 컴퓨터에 대입해 보면, **속도(Cruising speed)**는 작업 하나를 끝내는 데 걸리는 시간인 **응답 시간(Response Time)** 혹은 **지연 시간(Latency)**에 해당하고, **수송 효율(Throughput)**은 단위 시간당 처리하는 총 작업량인 **처리량(Throughput)**에 해당합니다.

사용자가 개인용 PC를 쓸 때는 응답 시간이 중요하겠지만, 대규모 데이터를 처리하는 서버실에서는 전체적인 처리량이 더 중요한 성능 지표가 됩니다. 따라서 성능을 논하기 전에는 반드시 "어떤 지표(Metric)를 기준으로 할 것인가"를 먼저 정의해야 합니다.

## 응답 시간(Response Time)과 처리량(Throughput) (Slides 6-7)

### Slide 6: 응답 시간과 처리량의 정의

컴퓨터 성능을 객관적으로 측정하기 위해서는 어떤 성능 지표(Performance metric)를 사용할 것인지 명확히 정의해야 합니다. 크게 두 가지 관점에서 성능을 정의할 수 있습니다.

첫째는 **응답 시간(Response time)**입니다. 실행 시간(Execution time) 혹은 경과 시간(Elapsed time)이라고도 불리며, 사용자가 작업을 시작해서 완료될 때까지 걸린 전체 시간을 의미합니다. 여기에는 단순히 CPU가 계산하는 시간뿐만 아니라 디스크 접근 시간, 메모리 접근 시간, 입출력(I/O) 활동 시간, 그리고 운영체제(OS)가 작업을 처리하는 데 소요되는 오버헤드까지 모두 포함됩니다. 주로 '초(seconds)' 단위로 측정하며, 개별 사용자 입장에서는 가장 체감하기 쉬운 지표입니다.

둘째는 **처리량(Throughput)**입니다. 이는 단위 시간당 처리하는 전체 작업의 양을 의미합니다. 예를 들어 '시간당 처리되는 트랜잭션 수'나 '초당 완료된 작업 수' 등이 해당합니다.

현대의 대형 서버나 공유 컴퓨터 시스템에서는 개별 프로그램의 실행 시간을 줄이는 것보다 시스템 전체의 처리량을 최적화하는 데 집중하기도 합니다. 프로세서는 한 번에 여러 프로그램을 번갈아 가며 수행할 수 있으므로, 개별 작업의 응답 시간은 다소 늘어나더라도 시스템 전체가 단위 시간당 처리하는 총 작업량을 극대화하는 것이 효율적일 수 있기 때문입니다.

### Slide 7: 하드웨어 변화가 성능 지표에 미치는 영향

우리가 시스템의 하드웨어 구성을 변경했을 때, 앞서 배운 두 지표가 어떻게 달라지는지 생각해보는 것은 매우 중요합니다. 다음 두 가지 사례를 통해 응답 시간과 처리량의 관계를 분석해 봅시다.

1.  **프로세서를 더 빠른 버전으로 교체하는 경우:**
    프로세서의 연산 속도가 빨라지면 개별 작업을 완료하는 데 걸리는 시간이 줄어듭니다. 따라서 **응답 시간**이 단축됩니다. 동시에 같은 시간 동안 더 많은 작업을 끝낼 수 있으므로 시스템의 **처리량**도 함께 향상됩니다. 즉, 이 경우에는 두 지표가 모두 개선됩니다.

2.  **프로세서를 추가로 장착(다중 프로세서 구성)하는 경우:**
    프로세서를 하나 더 추가한다고 해서 이미 실행 중인 '단일 작업'의 절대적인 연산 속도가 빨라지는 것은 아닙니다. 따라서 개별 작업의 **응답 시간**은 크게 변하지 않을 수 있습니다. 하지만 시스템이 동시에 여러 작업을 처리할 수 있게 되므로, 단위 시간당 완료하는 총 작업 수인 **처리량**은 확실하게 증가합니다.

이처럼 하드웨어의 개선 방식에 따라 영향을 받는 지표가 다를 수 있습니다. 이번 강의의 이어지는 내용에서는 성능 분석의 기초를 다지기 위해 주로 **응답 시간(Response time)**에 초점을 맞추어 논의를 진행하도록 하겠습니다.

## 상대적 성능과 실행 시간의 관계 (Slides 8-9)

### Slide 8: 성능의 정의와 상대적 성능의 수식화

두 컴퓨터의 성능을 객관적으로 비교하기 위해서는 '성능'이라는 추상적인 개념을 수치화할 수 있는 기준이 필요합니다. 컴퓨터 구조론에서 성능(Performance)은 실행 시간(Execution time)과 반비례 관계를 갖는다고 정의합니다. 즉, 어떤 작업을 완료하는 데 걸리는 시간이 짧을수록 성능은 높다고 평가합니다. 이를 수식으로 나타내면 다음과 같습니다.

$\text{Performance} = \frac{1}{\text{Execution time}}$

이 정의를 바탕으로 서로 다른 두 대의 컴퓨터 X와 Y의 성능을 비교해 봅시다. 만약 "컴퓨터 X의 성능이 Y보다 높다"고 한다면, 수학적으로 $\text{Performance}_X > \text{Performance}_Y$를 의미합니다. 앞서 정의한 반비례 관계를 대입하면 $\frac{1}{\text{Execution time}_X} > \frac{1}{\text{Execution time}_Y}$가 되며, 이는 결국 $\text{Execution time}_Y > \text{Execution time}_X$라는 결과로 이어집니다. 즉, 성능이 좋은 컴퓨터일수록 실행 시간은 더 짧습니다.

나아가 "X가 Y보다 $n$배 더 빠르다"는 문장을 정량적으로 표현할 수 있습니다. 이는 Y의 실행 시간을 X의 실행 시간으로 나눈 값, 혹은 X의 성능을 Y의 성능으로 나눈 비율로 계산합니다.

$n = \frac{\text{Performance}_X}{\text{Performance}_Y} = \frac{\text{Execution time}_Y}{\text{Execution time}_X}$

이 수식은 앞으로 우리가 다양한 하드웨어 설계안을 평가할 때 기준이 되는 가장 기본적인 지표가 될 것입니다.

### Slide 9: 실행 시간을 이용한 상대적 성능 계산 예시

앞서 배운 상대적 성능 수식을 실제 사례에 적용해 보겠습니다. 특정 프로그램을 실행하는 데 컴퓨터 A는 10초가 걸리고, 컴퓨터 B는 15초가 걸린다고 가정해 봅시다. 어느 컴퓨터가 더 빠르고, 얼마나 더 빠른지 계산해 보겠습니다.

우리는 "A가 B보다 얼마나 더 빠른가"를 구하고 싶으므로, 실행 시간이 더 긴 B를 분자에, 더 짧은 A를 분모에 둡니다.

$\frac{\text{Execution time}_B}{\text{Execution time}_A} = \frac{15s}{10s} = 1.5$

계산 결과 수치는 1.5가 나옵니다. 이를 성능의 관점에서 해석하면 "컴퓨터 A의 성능이 컴퓨터 B보다 1.5배 더 높다" 혹은 "A가 B보다 1.5배 더 빠르다"라고 말할 수 있습니다.

여기서 주의할 점은 '성능(Performance)'과 '실행 시간(Execution time)'의 위치가 서로 바뀐다는 것입니다. A가 1.5배 더 빠르다는 것은 A의 성능 수치가 B보다 1.5배 크다는 뜻이지만, 시간의 관점에서는 B가 A보다 1.5배 더 오래 걸린다는 의미입니다. 실무에서 성능 향상치를 보고할 때 이 두 개념을 혼동하지 않고 정확한 수식을 사용하는 것이 중요합니다.

## CPU 클럭 지표: Clock Rate 및 Clock Cycle (Slides 10-14)

### Slide 10: 성능 측정의 다양한 지표 (CPU Time과 CPI)

컴퓨터의 성능을 측정할 때 가장 근본적인 척도는 '시간'입니다. 하지만 시간도 측정 관점에 따라 두 가지로 나뉩니다.

첫째는 **경과 시간(Elapsed time)**입니다. 이는 앞서 설명한 응답 시간과 같은 개념으로, I/O 작업이나 OS 오버헤드, 유휴 시간(idle time)을 모두 포함한 전체 실행 시간입니다. 시스템 전체의 성능을 판단할 때 사용합니다.

둘째는 **CPU 시간(CPU execution time)**입니다. 이는 순수하게 CPU가 해당 작업을 처리하기 위해 소비한 시간만을 의미합니다. 여기에는 I/O 대기 시간이나 다른 프로그램이 CPU를 점유한 시간은 제외됩니다. CPU 시간은 다시 사용자 프로그램 자체에 쓰인 시간(User CPU time)과 운영체제가 프로그램을 돕기 위해 쓴 시간(System CPU time)으로 구분됩니다.

또한, 성능 분석을 위해 **CPI(Clock cycles Per Instruction)**라는 지표를 도입합니다. 이는 '명령어 하나를 실행하는 데 평균적으로 몇 개의 클럭 사이클이 필요한가'를 나타냅니다. CPI는 소프트웨어가 하드웨어 위에서 얼마나 효율적으로 실행되는지를 보여주는 핵심 지표입니다.

### Slide 11: CPU 클로킹(Clocking)의 개념

디지털 하드웨어의 모든 동작은 **일정한 속도의 클럭(Constant-rate clock)**에 의해 제어됩니다. 클럭 신호는 마치 오케스트라의 지휘자나 메트로놈과 같은 역할을 수행합니다.

슬라이드의 그림을 보면 클럭 신호가 '높음(High)'과 '낮음(Low)' 상태를 반복하며 진동하는 것을 볼 수 있습니다.

- **클럭 주기(Clock period):** 한 사이클이 완료되는 데 걸리는 시간입니다. 그림 상에서 한 산의 시작부터 다음 산의 시작까지의 거리를 의미합니다.
- **상태 업데이트(Update state):** 디지털 회로 내의 저장 장치(플립플롭, 래치 등)는 클럭 신호가 변하는 특정 시점에 맞춰 데이터를 저장하거나 다음 단계로 넘깁니다.

이러한 동기화 방식은 회로 내에서 데이터가 충돌하거나 순서가 뒤바뀌는 '경쟁 상태(Race condition)'를 방지하고 모든 구성 요소가 동시에 상태를 변경할 수 있도록 보장합니다.

### Slide 12: 클럭 주기와 클럭 주파수의 관계

클럭 성능을 표현하는 방법에는 두 가지가 있으며, 이 둘은 서로 역수 관계에 있습니다.

1.  **클럭 주기(Clock period):** 하나의 클럭 사이클이 지속되는 시간 간격입니다. 현대의 고속 CPU는 매우 짧은 주기를 가지며, 피코초($ps$)나 나노초($ns$) 단위를 사용합니다.
    - 예: $250ps = 0.25ns = 250 \times 10^{-12}s$
2.  **클럭 주파수(Clock frequency/rate):** 초당 발생하는 클럭 사이클의 횟수입니다. 헤르츠($Hz$) 단위를 사용합니다.
    - 예: $4.0GHz = 4,000MHz = 4.0 \times 10^{9}Hz$

수학적으로 **클럭 주파수 = 1 / 클럭 주기**입니다. 따라서 클럭 주파수가 높을수록(Rate가 클수록) 클럭 주기는 짧아지며, 이는 CPU가 더 빠른 간격으로 명령을 처리할 수 있음을 의미합니다. 하드웨어 사양표에서 흔히 볼 수 있는 '몇 GHz'라는 수치가 바로 이 클럭 주파수를 말합니다.

### Slide 13: CPU 실행 시간 계산 공식

이제 클럭 지표를 이용해 프로그램의 **CPU 실행 시간(CPU execution time)**을 계산하는 공식을 정의해 보겠습니다. 프로그램의 성능은 다음 수식으로 결정됩니다.

$\text{CPU execution time for a program} = \text{CPU Clock Cycles} \times \text{Clock Cycle Time}$

클럭 주기는 클럭 주파수의 역수이므로, 다음과 같이 표현할 수도 있습니다.

$\text{CPU execution time for a program} = \frac{\text{CPU Clock Cycles}}{\text{Clock Rate}}$

이 공식은 성능을 향상시키는 두 가지 명확한 방향을 제시합니다.

1.  **클럭 사이클 수 줄이기:** 알고리즘 최적화나 효율적인 컴파일을 통해 프로그램 실행에 필요한 총 클럭 수를 줄입니다.
2.  **클럭 주파수 높이기:** 하드웨어 기술력을 높여 CPU가 초당 더 많은 클럭을 발생시키게 합니다.

다만, 하드웨어 설계자는 클럭 주파수를 무작정 높이면 한 사이클 내에 처리해야 할 일이 많아져 전체 사이클 수가 늘어날 수 있다는 점을 고려해야 합니다. 즉, 클럭 속도(Rate)와 사이클 수(Cycle count) 사이의 적절한 트레이드 오프(Trade-off)가 필요합니다.

### Slide 14: CPU 성능 계산의 실제 사례

컴퓨터 A와 새롭게 설계할 컴퓨터 B를 비교하는 예제를 통해 공식을 적용해 봅시다.

- **조건:**
  - 컴퓨터 A: 클럭 주파수 $2GHz$, 실행 시간 $10s$
  - 컴퓨터 B: 목표 실행 시간 $6s$. 단, B의 클럭 속도를 높이면 설계상 A보다 $1.2$배 더 많은 클럭 사이클이 필요함.
- **계산 과정:**
  1.  먼저 컴퓨터 A의 총 클럭 사이클 수를 구합니다.
      $\text{Clock Cycles}_A = \text{CPU Time}_A \times \text{Clock Rate}_A = 10s \times 2 \times 10^{9}Hz = 20 \times 10^{9}$ cycles
  2.  컴퓨터 B에 필요한 총 클럭 사이클 수를 구합니다. (A의 $1.2$배)
      $\text{Clock Cycles}_B = 1.2 \times 20 \times 10^{9} = 24 \times 10^{9}$ cycles
  3.  목표 시간 $6s$를 달성하기 위한 B의 클럭 주파수를 계산합니다.
      $\text{Clock Rate}_B = \frac{\text{Clock Cycles}_B}{\text{CPU Time}_B} = \frac{24 \times 10^{9}}{6s} = 4 \times 10^{9}Hz = 4GHz$

결론적으로, 컴퓨터 B가 목표 성능을 달성하기 위해서는 클럭 주파수를 $4GHz$까지 끌어올려야 함을 알 수 있습니다. 이처럼 수식을 통해 구체적인 설계 목표를 설정할 수 있습니다.

## 명령어 성능 지표: CPI 및 CPU Time 공식 (Slides 15-24)

### Slide 15: 명령어 개수와 CPI의 정의

컴퓨터 성능을 결정하는 세 가지 핵심 요소인 명령어 개수(Instruction Count), CPI, 클럭 속도의 관계를 정의합니다.

1.  **명령어 개수(Instruction Count, IC):** 프로그램 실행을 위해 수행되는 총 명령어의 수입니다. 이는 실행되는 프로그램의 종류, 명령어 집합 구조(ISA), 그리고 코드를 기계어로 번역하는 컴파일러에 의해 결정됩니다.
2.  **평균 명령어당 사이클 수(Average cycles per instruction, CPI):** 명령어 하나를 실행하는 데 평균적으로 소요되는 클럭 사이클의 수입니다. 이는 CPU 하드웨어 설계 방식에 따라 결정되며, 명령어의 종류(믹스)에 따라 달라질 수 있습니다.

이 지표들을 결합하면 전체 클럭 사이클 수와 CPU 실행 시간을 다음과 같이 정의할 수 있습니다.

$\text{Clock Cycles} = \text{Instruction Count} \times \text{Cycles per Instruction}$
$\text{CPU Time} = \text{Instruction Count} \times \text{CPI} \times \text{Clock Cycle Time}$
$\text{CPU Time} = \frac{\text{Instruction Count} \times \text{CPI}}{\text{Clock Rate}}$

이 공식은 소프트웨어(IC)와 하드웨어(CPI, Clock Rate)가 어떻게 결합되어 전체 성능을 형성하는지 보여주는 가장 중요한 수식입니다.

### Slide 16: CPI와 클럭 주기를 이용한 성능 비교 사례

서로 다른 설계를 가진 두 컴퓨터 A와 B의 성능을 비교해 보겠습니다. 두 컴퓨터는 동일한 ISA를 사용하므로 명령어 개수($I$)는 같습니다.

- **컴퓨터 A:** 클럭 주기 $250ps$, CPI $2.0$
- **컴퓨터 B:** 클럭 주기 $500ps$, CPI $1.2$

각 컴퓨터의 CPU 실행 시간을 계산하면 다음과 같습니다.
$\text{CPU time}_A = I \times 2.0 \times 250ps = I \times 500ps$
$\text{CPU time}_B = I \times 1.2 \times 500ps = I \times 600ps$

두 값의 비율을 구하면 $\frac{\text{CPU time}_B}{\text{CPU time}_A} = \frac{I \times 600ps}{I \times 500ps} = 1.2$가 나옵니다.
결과적으로 컴퓨터 A가 B보다 $1.2$배 더 빠릅니다. 이 예제는 컴퓨터 B의 CPI가 더 낮음에도 불구하고(명령어당 효율은 좋으나), 컴퓨터 A의 클럭 속도가 월등히 빠르기 때문에 최종 성능은 A가 더 우세할 수 있음을 보여줍니다.

### Slide 17: 세부 명령어 클래스에 따른 가중 평균 CPI

실제 프로그램은 다양한 종류의 명령어로 구성되며, 각 명령어마다 실행에 필요한 사이클 수가 다릅니다. 따라서 더 정확한 계산을 위해 '가중 평균 CPI' 개념을 사용합니다.

전체 클럭 사이클 수는 각 명령어 클래스($i$)의 CPI와 해당 클래스의 명령어 개수($IC_i$)를 곱한 값들의 합으로 계산합니다.
$\text{Clock Cycles} = \sum_{i=1}^{n} (\text{CPI}_i \times \text{Instruction Count}_i)$

이를 바탕으로 전체 프로그램의 평균 CPI를 구하면 다음과 같습니다.
$\text{CPI} = \frac{\text{Clock Cycles}}{\text{Instruction Count}} = \sum_{i=1}^{n} (\text{CPI}_i \times \frac{\text{Instruction Count}_i}{\text{Instruction Count}})$

여기서 $\frac{\text{Instruction Count}_i}{\text{Instruction Count}}$는 전체 명령어 중 특정 클래스가 차지하는 비율인 **상대적 빈도(Relative frequency)**를 의미합니다. 즉, 전체 CPI는 각 명령어의 빈도와 개별 CPI가 결합된 결과물입니다.

### Slide 18: 명령어 시퀀스 비교를 통한 CPI 분석 예시

컴파일러가 동일한 작업을 수행하기 위해 두 가지 서로 다른 명령어 시퀀스를 생성했다고 가정해 봅시다. 명령어는 클래스 A(CPI 1), B(CPI 2), C(CPI 3)로 구성됩니다.

- **Sequence 1:** 클래스 A 2개, B 1개, C 2개 (총 $IC = 5$)
  - $\text{Clock Cycles} = (2 \times 1) + (1 \times 2) + (2 \times 3) = 10$
  - $\text{Avg. CPI} = \frac{10}{5} = 2.0$
- **Sequence 2:** 클래스 A 4개, B 1개, C 1개 (총 $IC = 6$)
  - $\text{Clock Cycles} = (4 \times 1) + (1 \times 2) + (1 \times 3) = 9$
  - $\text{Avg. CPI} = \frac{9}{6} = 1.5$

분석 결과, Sequence 2는 전체 명령어 개수($IC$)가 6개로 더 많지만, 상대적으로 실행 속도가 빠른 클래스 A 명령어를 많이 사용하여 전체 클럭 사이클 수는 9로 더 적습니다. 결과적으로 평균 CPI도 1.5로 더 낮습니다. 이는 명령어 개수가 적다고 해서 반드시 성능이 좋은 것은 아니며, 명령어의 구성(믹스)과 CPI의 조화가 더 중요하다는 사실을 증명합니다.

### Slide 19: 성능 결정 요소의 최종 요약

지금까지 배운 모든 내용을 종합하여 CPU 성능 방정식의 최종 형태를 정리합니다. 성능은 다음 세 가지 항의 곱으로 나타낼 수 있습니다.

$\text{CPU Time} = \frac{\text{Instructions}}{\text{Program}} \times \frac{\text{Clock cycles}}{\text{Instruction}} \times \frac{\text{Seconds}}{\text{Clock cycle}}$

각 항은 다음과 같은 요소들에 의해 영향을 받습니다.

- **알고리즘:** 명령어 개수($IC$)에 결정적인 영향을 미치며, 명령어 구성에 따라 평균 CPI에도 영향을 줄 수 있습니다.
- **프로그래밍 언어:** 문법의 구조에 따라 번역되는 명령어 개수와 구성이 달라지므로 $IC$와 CPI 모두에 영향을 줍니다.
- **컴파일러:** 코드를 얼마나 효율적인 명령어 시퀀스로 변환하느냐에 따라 $IC$와 CPI를 결정합니다.
- **명령어 집합 구조(ISA):** 하드웨어가 지원하는 명령어의 종류를 결정하므로 $IC$, CPI, 그리고 클럭 주기($T_c$) 모두에 관여하는 핵심 설계 요소입니다.

결론적으로 성능 최적화는 소프트웨어 계층과 하드웨어 계층이 만나는 모든 지점에서 동시에 이루어져야 합니다.

### CPU 성능 방정식의 3대 요소 분석 (Slide 19-1)

슬라이드 19에 제시된 수식은 컴퓨터의 성능을 결정하는 세 가지 독립적인 요소를 곱하여 전체 실행 시간을 구하는 **CPU 성능 방정식(CPU Performance Equation)**입니다. 각 항이 의미하는 바와 성능에 미치는 영향력을 구체적으로 살펴보겠습니다.

$\text{CPU Time} = \frac{\text{Instructions}}{\text{Program}} \times \frac{\text{Clock cycles}}{\text{Instruction}} \times \frac{\text{Seconds}}{\text{Clock cycle}}$

---

### 1항: 프로그램당 명령어 개수 (Instruction Count, IC)
$\frac{\text{Instructions}}{\text{Program}}$

이 항은 특정 프로그램을 실행하기 위해 수행되어야 하는 **총 명령어의 수**를 의미합니다. 소프트웨어적인 측면에서 결정되는 지표입니다.

*   **영향 요소:**
    *   **알고리즘:** 동일한 문제라도 효율적인 알고리즘은 더 적은 수의 연산(명령어)으로 작업을 끝냅니다.
    *   **프로그래밍 언어:** 고급 언어일수록 한 문장이 여러 개의 기계어 명령어로 번역될 수 있으며, 언어의 특성에 따라 생성되는 명령어의 양이 달라집니다.
    *   **컴파일러:** 컴파일러의 최적화 능력에 따라 동일한 소스 코드가 더 적고 효율적인 명령어 시퀀스로 변환될 수 있습니다.
    *   **ISA(명령어 집합 구조):** 하드웨어가 복잡하고 강력한 명령어를 지원할수록(CISC 등) 프로그램당 필요한 명령어의 절대적인 개수는 줄어듭니다.

---

### 2항: 명령어당 사이클 수 (Cycles Per Instruction, CPI)
$\frac{\text{Clock cycles}}{\text{Instruction}}$

이 항은 **명령어 하나를 실행하는 데 평균적으로 소요되는 클럭 사이클의 수**를 의미합니다. 하드웨어의 구조적 효율성을 나타내는 지표입니다.

*   **영향 요소:**
    *   **CPU 마이크로아키텍처:** 파이프라이닝(Pipelining)이나 슈퍼스칼라(Superscalar) 기술을 통해 명령어당 필요한 사이클 수를 1 미만으로 낮추거나 효율적으로 관리할 수 있습니다.
    *   **명령어 믹스(Instruction Mix):** 프로그램이 어떤 종류의 명령어(산술, 로드/스토어, 분기 등)를 많이 쓰느냐에 따라 달라집니다. 복잡한 연산은 더 많은 사이클을 소모하기 때문입니다.
    *   **ISA:** 명령어의 설계 방식이 단순하냐 복잡하냐에 따라 각 명령어를 처리하는 데 필요한 사이클 수가 결정됩니다. 일반적으로 RISC는 낮은 CPI를 지향합니다.

---

### 3항: 클럭 주기 (Clock Cycle Time, $T_c$)
$\frac{\text{Seconds}}{\text{Clock cycle}}$

이 항은 **하나의 클럭 사이클이 지속되는 시간**을 의미합니다. 이는 클럭 주파수(Clock Rate)의 역수($\frac{1}{\text{Clock Rate}}$)이며, 순수하게 하드웨어의 물리적인 속도 한계를 나타냅니다.

*   **영향 요소:**
    *   **반도체 제조 공정:** 트랜지스터의 크기가 작아지고 속도가 빨라질수록 클럭 주기를 단축할 수 있습니다.
    *   **하드웨어 설계 및 레이아웃:** 신호가 전달되는 경로의 길이나 게이트의 지연 시간을 최적화하여 클럭 속도를 높일 수 있습니다.
    *   **ISA:** 명령어 집합의 설계가 너무 복잡하면 한 사이클 내에 처리해야 할 일이 많아져 클럭 주기를 짧게 가져가는 데 방해가 될 수 있습니다.

---

### 수식의 종합적인 의미
이 세 가지 항을 모두 곱하면 분모와 분자가 서로 약분되어 최종적으로 **$\frac{\text{Seconds}}{\text{Program}}$(프로그램당 소요 시간)**만 남게 됩니다. 

결론적으로 성능을 높이기 위해서는 어느 한 요소만 개선해서는 부족합니다. 예를 들어, 클럭 속도(3항)를 억지로 높였는데 그 과정에서 명령어 처리 로직이 복잡해져서 CPI(2항)가 급격히 상승한다면 전체적인 실행 시간은 오히려 늘어날 수 있습니다. 따라서 하드웨어 설계자와 소프트웨어 개발자는 이 세 가지 요소 사이의 긴밀한 상관관계를 이해하고 전체적인 균형을 맞추는 최적화 작업을 수행해야 합니다.

### Slide 20: CPU와 그 구성 요소 단원의 시작
앞서 우리는 성능이라는 추상적인 지표와 이를 계산하는 수식들을 학습했습니다. 이제부터는 그 성능이 실제로 구현되는 물리적 실체인 CPU와 그 주변 하드웨어 구성 요소들에 대해 알아보겠습니다. 

이 단원에서는 명령어(Instruction)가 실제로 하드웨어 상에서 어떻게 이동하고 처리되는지를 다룹니다. 성능 공식에서 보았던 클럭 주기나 명령어 실행 과정이 물리적으로 어떻게 이루어지는지 이해하는 것은 컴퓨터 구조의 설계 원리를 파악하는 첫걸음입니다. 슬라이드에 제시된 참고 문헌들처럼, 하드웨어의 내부 구조를 아는 것은 효율적인 소프트웨어를 작성하는 데에도 큰 도움이 됩니다.

### Slide 21: CPU, 메모리, 입출력 장치의 상호작용
컴퓨터 시스템은 크게 연산을 담당하는 CPU(Processing unit)와 데이터를 저장하는 메모리(Storage unit)로 나뉩니다. 두 장치는 세 가지 통로를 통해 정보를 주고받습니다.

1.  **주소(Address):** CPU가 메모리의 어느 위치에 있는 데이터를 읽거나 쓸 것인지 지정하는 신호입니다.
2.  **데이터(Data):** 실제 처리될 수치나 정보가 이동하는 통로입니다.
3.  **명령어(Instruction):** CPU가 수행해야 할 동작이 담긴 코드가 메모리로부터 전달됩니다.

CPU 내부에서는 데이터 이동, 산술 및 논리 연산, 제어 흐름 변경(Control transfer)이 일어납니다. 반면 메모리는 바이트 단위로 주소가 부여된 배열 형태이며, 이곳에는 사용자 프로그램의 코드와 데이터, 그리고 서브루틴 호출을 위한 스택(Stack) 등이 저장됩니다. 결국 컴퓨터의 동작은 CPU가 메모리로부터 명령어를 가져와 해석하고, 필요한 데이터를 주소에 맞춰 읽거나 쓰는 과정의 반복입니다.

### Slide 22: 마이크로컴퓨터의 기본 구성 요소와 시스템 버스
실제 마이크로컴퓨터의 내부 구조는 조금 더 복잡합니다. 슬라이드의 그림은 CPU, 칩셋, 메모리(ROM/RAM), 그리고 입출력 장치들이 어떻게 유기적으로 연결되는지 보여줍니다.

여기서 가장 중요한 개념은 **시스템 버스(System bus)**입니다. 시스템 버스는 주소 버스, 데이터 버스, 제어 버스로 구성되어 있으며, CPU와 메모리, 그리고 각종 제어 칩셋들을 하나로 연결하는 중추적인 역할을 합니다. 
*   **CPU부:** 연산의 핵심인 CPU와 주변 회로를 보조하는 칩셋이 포함됩니다.
*   **메모리부:** 전원이 꺼져도 유지되는 ROM과 작업 공간인 RAM이 버스에 매달려 있습니다.
*   **입출력장치 접속부:** 키보드와 같은 입력 장치나 모니터와 같은 출력 장치가 시스템 버스와 소통할 수 있도록 인터페이스 역할을 합니다.

이 모든 구성 요소가 공통된 버스를 공유하기 때문에, 한 번에 하나의 장치만 버스를 사용할 수 있도록 정교한 제어가 필요합니다.

### Slide 23: 버스(Bus)의 정의와 물리적 특징
버스는 정보를 교환하기 위해 CPU와 하드웨어 요소들을 연결해주는 **신호선들의 집합**입니다. 우리가 흔히 메인보드 바닥에서 볼 수 있는 구리선들이나 케이블들이 바로 버스의 물리적 실체입니다.

*   **정보의 형태:** 버스를 통해 이동하는 정보는 0 또는 1로 구성된 2진 데이터입니다. 전압의 높고 낮음으로 이 신호를 구분합니다.
*   **물리적 구조:** 전자회로 부품들을 연결하는 수많은 신호선들의 다발로 이루어져 있습니다.
*   **설치 방식:** 하드웨어 제조 단계에서 이미 배선이 고정된 전선(Hard-wired)들의 집합체입니다.

버스의 폭(선로의 개수)은 한 번에 보낼 수 있는 데이터의 양을 결정하며, 이는 컴퓨터의 비트 수(예: 32비트, 64비트)를 정의하는 기준이 되기도 합니다.

### Slide 24: 버스의 종류와 역할 분담
시스템 버스는 기능에 따라 크게 세 가지 유형으로 나뉩니다. 각 버스의 특성을 이해하는 것이 중요합니다.

1.  **주소 버스(Address bus):** CPU가 데이터를 읽거나 쓸 메모리 위치를 알려주는 통로입니다. CPU에서 외부로 신호를 보내기만 하는 **단방향 전송** 방식입니다. 주소 버스의 선로 수(폭)는 컴퓨터가 인식할 수 있는 최대 메모리 용량을 결정합니다. 예를 들어, 폭이 16비트라면 $2^{16} = 65,536$개의 위치를 지정할 수 있습니다.
2.  **데이터 버스(Data bus):** CPU와 메모리 혹은 I/O 장치 간에 실제 데이터를 주고받는 통로입니다. 양쪽으로 데이터가 흐르므로 **양방향 전송** 방식입니다. 데이터 버스의 폭은 한 번에 전송할 수 있는 비트 수를 결정하며 시스템의 처리 성능에 직결됩니다.
3.  **제어 버스(Control bus):** CPU가 주변 장치에 특정 동작(읽기, 쓰기 등)을 명령하거나 장치의 상태를 확인하기 위한 신호선입니다. 읽기/쓰기 신호, 인터럽트 신호 등이 포함되며, 상황에 따라 단방향 또는 양방향 전송이 이루어집니다.

이 세 가지 버스가 조화롭게 작동해야만 CPU가 정확한 위치에서 데이터를 가져와 연산하고 결과를 저장하는 일련의 과정을 성능 지표에 맞춰 수행할 수 있습니다.

# 2. CPU 구조와 주요 구성 요소 (Slides 25-44)

## CPU의 기본 구조: 제어 장치와 데이터패스 (Slides 25-29)

### Slide 25: 시스템 버스의 물리적 연결 구조
컴퓨터 내부의 각 장치가 물리적으로 어떻게 연결되어 신호를 주고받는지 시각화한 자료입니다. CPU, 메모리(Memory), 그리고 입출력 장치(I/O device)는 앞서 배운 세 가지 버스를 통해 그물망처럼 연결되어 있습니다.

그림에서 파란색 선으로 표시된 **데이터 버스(Data bus)**는 16개의 선(16 wires)으로 구성된 예시를 보여주며, 이는 한 번에 16비트의 데이터를 양방향으로 전송할 수 있음을 의미합니다. 빨간색의 **주소 버스(Address bus)**는 CPU가 지정한 특정 메모리 위치나 I/O 포트로 신호를 전달하며, 분홍색의 **제어 버스(Control bus)**는 읽기(Read) 또는 쓰기(Write)와 같은 제어 명령을 전달합니다. 특정 장치에 데이터가 도달하기 위해서는 주소 버스가 해당 장치를 지목하고, 제어 버스가 동작을 승인하며, 최종적으로 데이터 버스를 통해 정보가 이동하는 일련의 조화가 필요합니다.

### Slide 26: 버스의 읽기 및 쓰기 동작 원리
CPU와 RAM 사이에서 데이터가 교환되는 구체적인 시간 흐름(Timing diagram)을 보여줍니다. 모든 동작은 제어 신호의 변화에 따라 단계적으로 일어납니다.

1.  **기억장치 쓰기 동작 (a):** CPU는 먼저 주소 버스에 데이터를 저장할 '주소'를 싣고, 데이터 버스에 실제 '내용'을 실어 보냅니다. 그 후 '쓰기 신호(Write signal)'를 활성화(High 상태로 전환)하여 메모리가 데이터를 저장하도록 명령합니다.
2.  **기억장치 읽기 동작 (b):** CPU가 주소 버스에 읽고자 하는 '주소'를 전송하고 '읽기 신호(Read signal)'를 보냅니다. 메모리는 해당 주소를 확인한 후 일정 시간이 지나면 데이터 버스에 '내용'을 실어 CPU로 전달합니다.

기억장치 **읽기** 동작에서 데이터 버스가 늦는 이유는 정보의 **생성 주체**가 다르기 때문입니다. CPU가 주소를 보내면, 메모리는 해당 주소를 해독하고 내부에서 데이터를 찾아 증폭하는 물리적 처리 시간(액세스 지연)이 필요합니다. 즉, 메모리가 답변을 준비해 버스에 실을 때까지의 시차가 발생하는 것입니다.

반면, **쓰기** 동작에서는 주소와 데이터 모두 생성 주체가 **CPU**로 동일합니다. CPU 내부에 저장할 위치와 내용이 이미 준비되어 있으므로, 두 정보를 동시에 버스에 실어 보내는 것이 가장 효율적입니다. 또한, 메모리가 '쓰기 신호'를 받기 전 주소와 데이터 전압이 미리 안정화되어야 정확한 기록이 가능하므로(Setup Time 확보), 시차를 두지 않고 즉시 전송하여 처리 성능을 극대화합니다.

요약하자면, **읽기**는 메모리의 '찾아오는 시간'을 기다려야 해서 데이터가 늦게 도달하고, **쓰기**는 CPU가 모든 정보를 한꺼번에 '밀어 넣기' 때문에 동시에 전송됩니다.

이 과정에서 신호가 안정화될 때까지 기다리는 미세한 지연 시간이 존재하며, CPU 성능을 극대화하기 위해서는 이 버스 점유 시간을 효율적으로 관리하는 것이 핵심입니다.

### Slide 27: 현대적 컴퓨터 구조의 계층화
고성능 컴퓨터나 서버급 시스템에서 사용하는 발전된 구조를 보여줍니다. 단순히 CPU와 메모리가 직접 연결되는 것이 아니라, 효율적인 데이터 관리를 위해 중간에 제어 장치들이 개입합니다.

중앙처리장치(CPU)는 **시스템 버스**를 통해 **메모리 컨트롤러(Memory Controller/Chipset)**와 연결되며, 이는 다시 고속의 메모리(RAM)와 소통합니다. 반면 마우스, 키보드, 모니터, 하드디스크(HDD)와 같은 주변 장치들은 상대적으로 속도가 느리기 때문에 **I/O 컨트롤러(Chipset)**를 거쳐 **I/O 버스**를 통해 연결됩니다. 서버급 기종은 성능을 높이기 위해 다중 프로세서 구조를 취하며, 에러 검출 및 정정 기능이 강화된 고가의 소자를 사용하여 시스템의 안정성을 확보합니다.

### Slide 28: 주소 체계와 컨트롤러의 구분
하드웨어 자원을 효율적으로 관리하기 위해 주소와 컨트롤러는 메모리용과 입출력(I/O)용으로 명확히 구분됩니다.

*   **주소의 구분:** 메모리 주소(Memory address)는 주로 휘발성 저장소인 RAM의 위치를 지정하는 데 사용됩니다. 반면 I/O 주소(I/O address)는 키보드, 마우스뿐만 아니라 보조기억장치인 HDD/SSD 등을 지정하는 데 쓰입니다. 하드웨어 설계 관점에서 HDD는 저장 장치이지만 물리적으로는 I/O 장치로 분류된다는 점이 특징입니다.
*   **컨트롤러의 역할:** CPU가 모든 하드웨어를 직접 제어하는 것은 비효율적입니다. 따라서 **메모리 컨트롤러**가 메모리 장치를 전담 관리하고, **I/O 컨트롤러**가 입출력 장치를 제어합니다. 이러한 컨트롤러들은 대개 **칩셋(Chipset)** 형태로 메인보드에 구현되어 CPU의 연산 부담을 덜어줍니다.

### Slide 29: 시스템 버스와 I/O 버스의 기능적 차이
컴퓨터 내부에는 용도와 속도에 따라 서로 다른 종류의 버스가 존재합니다.

1.  **시스템 버스(System bus):** CPU, 메인 메모리, 그리고 핵심 칩셋들을 연결하는 고속 통로입니다. 특히 RAM 모듈을 CPU의 동작 속도에 맞춰 동기화(Synchronize)시키는 역할을 하여 제어 시간을 절약하고 데이터 전송 효율을 극대화합니다.
2.  **I/O 버스(I/O bus):** I/O 컨트롤러와 실제 입출력 장치들 사이를 연결합니다. 주변 장치들은 종류가 매우 다양하고 속도도 제각각이기 때문에, 비트 수와 전송 속도가 다양한 여러 종류의 I/O 버스(예: USB, PCI Express 등)가 혼용되어 사용됩니다.

결론적으로 현대 컴퓨터 아키텍처는 고속 연산이 필요한 부분(시스템 버스 영역)과 범용적인 확장이 필요한 부분(I/O 버스 영역)을 분리하여 설계함으로써 시스템 전체의 병목 현상을 최소화합니다.

## 레지스터(Registers): 유형 및 역할 (Slides 30-38)

### Slide 30: I/O 버스 처리 과정과 제어기 레지스터
입출력(I/O) 장치는 CPU보다 동작 속도가 매우 느리기 때문에 CPU가 직접 장치를 제어하는 대신 '제어기(Controller)'라는 중간 장치를 거칩니다. 이 슬라이드는 CPU가 시스템 버스를 통해 키보드 제어기나 프린터 제어기와 소통하는 구조를 보여줍니다.

각 제어기 내부에는 핵심적인 두 가지 레지스터가 존재합니다.
1.  **상태 레지스터(Status Register):** 장치가 현재 데이터를 보낼 준비가 되었는지, 혹은 오류가 발생했는지 등 장치의 상태 정보를 비트 단위로 저장합니다.
2.  **데이터 레지스터(Data Register):** 실제 입출력되는 데이터(예: 키보드에서 입력된 문자 코드)를 일시적으로 보관하는 장소입니다.

CPU는 주소 버스를 통해 특정 제어기를 지목하고, 제어 버스로 읽기/쓰기 신호를 보낸 뒤, 데이터 버스를 통해 이 레지스터들의 값을 읽거나 씁니다. 이러한 구조 덕분에 CPU는 복잡한 하드웨어 신호를 직접 다루지 않고 레지스터 값을 확인하는 것만으로 I/O 작업을 수행할 수 있습니다.

### Slide 31: I/O 버스 처리 예시 (키보드 입력과 폴링)
키보드로부터 데이터를 읽어오는 구체적인 과정을 통해 레지스터의 역할을 살펴봅니다. 사용자가 키보드의 한 키를 누르면 다음 단계가 진행됩니다.

1.  **키보드 제어기 동작:** 눌린 키에 해당하는 ASCII 코드가 제어기 내부의 **데이터 레지스터**에 저장됩니다. 이와 동시에 **상태 레지스터**의 특정 비트(In_RDY)가 1(Set)로 바뀝니다. 이는 "데이터가 준비되었다"는 신호입니다.
2.  **CPU의 확인 작업:** CPU는 루프를 돌며 키보드 제어기의 상태 레지스터 내용을 반복적으로 읽습니다. 이를 **폴링(Polling)** 방식이라고 합니다. 
3.  **조건 판단:** 만약 In_RDY 비트가 0이면 데이터가 아직 없는 것이므로 반복해서 대기합니다. 비트가 1이 되는 순간, CPU는 데이터 레지스터에 접근하여 ASCII 코드를 읽어옵니다.

오른쪽 순서도는 이 논리적 흐름을 명확히 보여줍니다. 레지스터는 이처럼 CPU와 외부 장치 사이에서 속도 차이를 극복하고 작업의 완료 여부를 알려주는 동기화 도구로 활용됩니다.

### Slide 32: 칩셋(Chipset)의 정의와 기능
칩셋은 메인보드 상에서 여러 개의 제어 칩과 회로를 하나로 모아 서로 연관된 기능을 수행하도록 설계된 제어 장치들의 조합(Set)입니다. 컴퓨터뿐만 아니라 스마트폰, 디지털 TV 등 모든 전자제품에는 해당 시스템에 최적화된 특수 목적용 칩셋이 탑재됩니다.

칩셋의 주요 역할은 다음과 같습니다.
*   **시스템 전체 제어:** CPU 프로세서와 협력하여 하드웨어 자원을 효율적으로 관리합니다. 특정 CPU가 시스템의 다른 부품들과 원활하게 통신할 수 있도록 돕는 일종의 '비서' 역할을 합니다.
*   **내부 구성 요소:** 칩셋 내부에는 버스 제어기(Bus controller), 메모리 제어기(Memory controller), I/O 제어기, 인터럽트 제어기, 타이머 등 시스템 운영에 필수적인 각종 제어 장치들이 집약되어 있습니다.

과거에는 수많은 개별 칩으로 나뉘어 있던 기능들이 기술의 발전으로 몇 개의 칩셋으로 통합되었으며, 이는 시스템의 크기를 줄이고 성능을 높이는 결과를 가져왔습니다.

### Slide 33: 칩셋의 전통적 구성 (North/South Bridge)
전통적인 칩셋 구조는 속도와 역할에 따라 두 개의 핵심 브리지(Bridge)로 나뉩니다.

1.  **노스브리지(North bridge):** CPU 근처에 위치하며, 메모리(RAM) 제어기와 고속 그래픽 인터페이스를 포함합니다. 데이터 전송량이 많고 속도가 매우 빠른 장치들을 담당하기 때문에 시스템 성능에 직접적인 영향을 미칩니다. 이를 **MCH(Memory Controller Hub)**라고도 부릅니다.
2.  **사우스브리지(South bridge):** 상대적으로 속도가 느린 입출력 장치들을 담당합니다. USB, SATA(디스크), 오디오, 네트워크 등을 제어하며, 이를 **ICH(I/O Controller Hub)** 또는 **IOH**라고 부릅니다.

이 두 브리지는 각각의 장치들을 CPU와 연결해주는 '중심 연결 장치(Hub)' 역할을 수행하며, 시스템 내에서 데이터가 흐르는 주요 통로가 됩니다.

### Slide 34: 칩셋 구조의 진화와 병목 현상 해결
슬라이드의 다이어그램은 프로세서와 칩셋 간의 연결 구조를 보여주며, 하드웨어 설계의 진화 과정을 설명합니다.

*   **병목 현상(Bottleneck):** 과거 구조에서는 모든 데이터가 노스브리지를 거쳐 CPU로 전달되었습니다. 시스템의 성능이 올라갈수록 노스브리지에 데이터가 집중되면서 전체 속도가 저하되는 병목 현상이 발생했습니다.
*   **해결책 (Integration):** 이 문제를 해결하기 위해 현대의 아키텍처는 **노스브리지의 기능을 CPU 프로세서 칩 내부로 통합**하는 방식을 취합니다. 
*   **FSB(Front-Side Bus):** CPU와 노스브리지를 잇던 통로인 FSB를 거치지 않고 CPU가 메모리에 직접 접근하게 됨으로써 지연 시간을 획기적으로 줄였습니다. 

결과적으로 칩셋은 CPU 외부의 독립적인 장치에서 CPU의 일부 기능으로 흡수되는 추세이며, 이는 시스템의 통합성과 효율성을 극대화하는 방향으로 발전하고 있습니다.

### Slide 35: 칩셋 구성의 현대적 추세
칩셋 설계의 핵심 트렌드는 '통합'과 '전문화'입니다. 과거 메인보드에 흩어져 있던 기능들이 점차 CPU 내부로 흡수되는 과정을 보여줍니다.

1.  **비디오 인터페이스 내장:** 과거 노스브리지에 포함되던 그래픽 전용 채널이 성능 향상을 위해 CPU 내부로 들어왔습니다. 특히 저가형 설계에서는 GPU(Graphic Processing Unit) 자체가 CPU 안에 내장되는 형태가 일반화되었습니다.
2.  **노스브리지의 CPU 통합:** 메모리(RAM) 모듈, 비디오 채널, 사우스브리지로 가는 통로를 각각 독립적인 채널로 분리했습니다. 이를 통해 과거 모든 데이터가 한곳에 몰려 발생하던 **FSB(Front-Side Bus)의 병목 현상**을 근본적으로 해결했습니다. 또한, RAM 접근 속도가 빨라지면서 멀티코어 프로세서의 성능이 비약적으로 향상되었습니다.
3.  **PCH(Platform Controller Hub)의 등장:** 인텔의 사례처럼 전통적인 노스브리지의 핵심 기능(메모리 제어 등)은 CPU가 가져가고, 남은 노스브리지의 일부 기능과 사우스브리지 기능을 합쳐 하나의 PCH 칩으로 통합했습니다.

최근에는 이 PCH마저도 프로세서 칩 안에 모두 내장하여 시스템을 원칩(One-chip)화하는 추세입니다.

### Slide 36: 인텔 4세대 Core 프로세서 플랫폼 (Haswell, 2013.09)
2013년 출시된 인텔 4세대 아키텍처의 블록 다이어그램을 통해 구체적인 연결 구조를 확인할 수 있습니다.

*   **프로세서(Processor) 영역:** CPU 내부에 **노스브리지 기능이 내장**되어 있습니다. 시스템 메모리(System Memory)와 연결되는 CH A, CH B라는 **독립적인 채널**이 존재하여 고속의 데이터 전송($1333/1600 MT/s$)이 가능해졌습니다. 또한 PCI Express 3.0 및 디지털 디스플레이 인터페이스(DDI)가 프로세서에 직접 연결됩니다.
*   **PCH(Platform Controller Hub) 영역:** 그림 중앙의 녹색 원으로 표시된 부분입니다. 여기에는 **전통적인 사우스브리지 기능**에 더해 노스브리지의 일부 기능이 통합되어 있습니다. USB 3.0, SATA 6 GB/s, 오디오, 기가비트 랜 등이 이 PCH를 통해 제어됩니다.
*   **진화의 예고:** 슬라이드 우측 상단의 주석을 보면, 5세대 프로세서부터는 이 PCH 영역마저도 CPU 칩 내부로 완전히 내장될 것임을 예고하고 있습니다.

### Slide 37: 인텔 5세대 Core 프로세서 플랫폼 (Broadwell, 2015.01)
5세대 프로세서에 이르러 하드웨어 통합은 정점에 달합니다. 슬라이드 상단의 설명처럼 **CPU와 같은 반도체 기판(Die) 위에 칩셋 기능을 완전히 내장**한 형태입니다.

중앙의 인텔 프로세서 아이콘을 중심으로 모든 주변 장치가 거미줄처럼 직접 연결된 구조를 볼 수 있습니다.
*   **고속 장치:** DDR3L/LPDDR3 메모리, SSD(SATA), 디스플레이 장치 등이 프로세서와 직결됩니다.
*   **다양한 인터페이스:** 카메라, BIOS, TPM(보안 칩), 터치스크린, 지문 인식 센서, 오디오 코덱뿐만 아니라 Wi-Fi/WiMax, NFC, SD 슬롯까지 하나의 플랫폼 안에서 모두 제어됩니다.

이러한 고밀도 통합은 데이터 전송 거리(Latency)를 단축시켜 성능을 높일 뿐만 아니라, 전력 소모를 줄이고 기기의 크기를 소형화하는 데 결정적인 기여를 했습니다.

### Slide 38: 중앙처리장치(CPU)의 정의와 역할
칩셋과의 관계를 넘어 CPU 본연의 기능과 명칭의 정의를 다시 정리합니다. CPU의 핵심 임무는 **명령어(Instruction)와 데이터(Data)를 처리**하는 것입니다.

1.  **동작 원리:** 프로그램이 명령어를 내리면 이를 메모리에서 인출(Fetch)하여 해독(Decode)합니다. 그 결과에 따라 필요한 데이터를 가져와 연산을 수행하고, 다시 저장하거나 다른 장치로 전송합니다.
2.  **용어의 구분:**
    *   **Process(프로세스):** 연산이나 데이터 처리를 위해 현재 실행 중인 작업이나 프로그램을 의미하는 소프트웨어적 개념입니다.
    *   **Processing(프로세싱):** 이러한 작업이 진행되는 처리 과정 그 자체를 말합니다.
    *   **Processor(프로세서):** 하드웨어적 실체입니다. 컴퓨터 내부에 포함된 하나의 모듈이자 CPU 칩, 혹은 컴퓨터 시스템 그 자체를 지칭하기도 합니다.

슬라이드 우측 하단의 Intel Core i7 칩 사진은 우리가 일상적으로 접하는 하드웨어 프로세서의 실제 모습을 대변합니다. 결국 CPU는 컴퓨터라는 거대한 오케스트라의 지휘자이자 연주자인 셈입니다.

## 산술 논리 장치(ALU)와 레지스터 (Slides 39-44)

### Slide 39: 중앙처리장치(CPU)의 3대 핵심 구성 요소
CPU 내부에서 실제 데이터 처리를 담당하는 세 가지 핵심 하드웨어 요소를 정의합니다.

1.  **산술 논리 연산 장치(ALU):** 이름 그대로 더하기, 빼기 같은 **산술 연산**과 AND, OR, XOR 같은 **논리 연산**을 실제로 수행하는 하드웨어 부품입니다. CPU의 '계산기' 역할을 수행합니다.
2.  **레지스터(Register):** 연산을 위해 필요한 데이터를 아주 짧은 시간 동안 보관하는 **일시적인 기억장소**입니다. 메모리(RAM)보다 훨씬 빠르지만 용량이 매우 작으며, 연산 과정의 중간 값이나 명령어, 주소 등을 저장합니다.
3.  **제어 장치(Control unit):** 명령어를 해석하여 시스템의 각 부품에 **제어 신호(Control signal)**를 보내는 역할을 합니다. 연산, 읽기, 쓰기 등의 동작 신호와 정확한 시점을 알려주는 **타이밍(Timing) 신호**를 발생시켜 전체 시스템의 흐름을 지휘합니다.

결국 CPU는 제어 장치가 명령을 내리고, 레지스터가 데이터를 공급하며, ALU가 계산을 수행하는 유기적인 협력을 통해 동작합니다.

### Slide 40: CPU 내부 데이터 흐름의 시각화
이 슬라이드는 CPU 내부의 물리적인 배치와 데이터가 이동하는 경로를 보여줍니다.

*   **내부 데이터 버스(Internal data bus):** CPU 내부에서 ALU, 제어 장치, 레지스터들 사이를 잇는 고속 통로입니다. 외부 시스템 버스와 분리되어 CPU 내부 장치들끼리만 빠르게 정보를 주고받습니다.
*   **I/O 유닛:** 외부 데이터 버스(시스템 버스 혹은 프론트 사이드 버스)와 연결되어 메모리나 입출력 장치와 데이터를 주고받는 게이트웨이 역할을 합니다.
*   **배치 구조:** 외부에서 들어온 데이터는 I/O 유닛을 통해 내부 버스로 진입하며, 레지스터에 보관되었다가 ALU에서 연산됩니다. 제어 장치는 이 모든 과정이 순서대로 일어나도록 각 장치에 신호를 보냅니다.

이 구조를 통해 CPU가 독립적인 내부 네트워크를 가지고 외부 환경과 격리되어 고속 연산을 수행함을 알 수 있습니다.

### Slide 41: 레지스터(Register) 단원의 시작
이제 CPU 내부 저장 공간인 레지스터에 대해 상세히 알아봅니다. 앞서 설명했듯이 레지스터는 CPU 내부에 존재하는 '가장 빠른 저장소'입니다. 

슬라이드 우측의 교재 표지들이 보여주듯, 레지스터의 설계와 활용 방식은 컴퓨터 아키텍처 연구의 고전적이면서도 가장 중요한 주제 중 하나입니다. 연산 장치(ALU)가 아무리 빨라도 데이터를 공급하는 레지스터가 효율적이지 못하면 전체 성능은 떨어질 수밖에 없습니다. 다음 슬라이드부터는 레지스터가 구체적으로 어떻게 구성되고 각 명칭이 무엇인지 살펴보겠습니다.

### Slide 42: 레지스터의 기본 구성과 명칭
CPU 내부에는 용도에 따라 이름이 붙여진 여러 개의 특수 목적 레지스터가 존재합니다. 슬라이드의 다이어그램은 이들의 연결 관계를 보여줍니다.

*   **AC (Accumulator):** 연산 결과를 일시적으로 저장하는 누산기입니다.
*   **PC (Program counter):** 다음에 실행할 명령어의 주소를 가리킵니다.
*   **MAR (Memory address register):** 메모리에서 데이터를 읽거나 쓸 때 해당 주소를 일시 저장합니다.
*   **MBR (Memory buffer register):** 메모리와 주고받는 실제 데이터를 일시 저장합니다.
*   **IR (Instruction register):** 현재 실행 중인 명령어를 저장합니다.

이 레지스터들은 내부 버스를 통해 ALU 및 제어 장치와 연결되어 있으며, 명령어가 실행되는 단계마다 각자의 역할을 수행하며 데이터의 징검다리 역할을 합니다.

### Slide 43: 주요 가상 레지스터의 기능 정의
대표적인 레지스터들의 구체적인 임무를 정리합니다.

1.  **Accumulator (AC):** 연산에 가장 빈번하게 사용되며, 연산 결과가 다시 자신에게 누적($accumulation$)되는 특성이 있습니다.
2.  **Program counter (PC):** 다음에 인출해 올 명령어의 주소를 저장하여 프로그램의 실행 순서를 제어합니다.
3.  **MAR & MBR:** 주소 버스로 나갈 주소는 MAR에, 데이터 버스로 오갈 데이터는 MBR에 임시 보관합니다. 버스와 CPU 사이의 완충 지대 역할을 합니다.
4.  **Instruction register (IR):** 가장 최근에 메모리에서 가져온 명령어를 담고 있으며, 제어 장치는 이 IR의 내용을 해석합니다.
5.  **기타 범용 레지스터:** 연산 도중 임시 값을 저장하는 용도로 쓰이며, 제조사마다 개수와 명칭이 다릅니다. 예로 주소를 저장하는 Pointer나 개수를 세는 Counter 등이 있습니다.

실제 프로세서에서는 슬라이드에 명시된 것처럼 이보다 훨씬 많은 수의 레지스터를 사용하며, 그 명칭 또한 아키텍처마다 고유하게 정의됩니다.

### Slide 44: 현대적 아키텍처 사례: RISC-V 레지스터 세트
현대적인 오픈 소스 아키텍처인 **RISC-V**의 실제 레지스터 구성을 표로 보여줍니다.

*   **범용 레지스터 (x0~x31):** 총 32개의 정수 레지스터가 존재합니다. 
    *   `x0`는 항상 0을 유지하는 상수 레지스터입니다.
    *   `ra(x1)`는 함수 호출 후 돌아갈 주소를 저장합니다.
    *   `sp(x2)`는 스택 포인터로 사용됩니다.
    *   `a0-a7(x10-x17)`은 함수의 인자나 결과값을 전달하는 데 쓰입니다.
*   **부동 소수점 레지스터 (f0~f31):** 소수점 연산을 위한 별도의 32개 레지스터가 있습니다.
*   **Saver (Caller/Callee):** 함수 호출 시 누가 데이터를 보존해야 하는지에 대한 규칙(ABI)이 정의되어 있어, 컴파일러가 효율적으로 레지스터를 사용할 수 있게 합니다.

이처럼 이론적인 레지스터 개념은 RISC-V와 같은 실제 아키텍처에서 구체적인 이름과 용도가 부여되어 동작하게 됩니다.

# **3. 명령어 집합 구조(ISA) 및 분류 (Slides 45-69)**

## ISA의 정의와 하드웨어-소프트웨어 인터페이스 (Slides 45-50)

### Slide 45: 산술 논리 연산 장치(ALU) 단원의 시작
이제 CPU의 핵심 계산 엔진인 **산술 논리 연산 장치(Arithmetic and Logic operation Unit, ALU)**에 대해 구체적으로 학습하겠습니다. 앞서 배운 레지스터들이 데이터를 보관하는 '그릇'이라면, ALU는 그 데이터를 실제로 가공하여 결과물을 만들어내는 '공장'과 같습니다.

이 단원에서는 수치 데이터의 덧셈, 뺄셈뿐만 아니라 비트 단위의 논리 연산이 하드웨어적으로 어떻게 구현되는지, 그리고 연산 결과의 상태(양수, 음수, 오버플로우 등)를 어떻게 관리하는지 다룹니다. ALU는 제어 장치로부터 명령을 받아 레지스터에 저장된 피연산자들을 처리하며, 그 결과는 다시 레지스터에 저장되거나 시스템의 다음 동작에 영향을 미칩니다.

### Slide 46: ALU의 일반적인 구성 요소
ALU는 단순히 계산만 하는 장치가 아니라, 다양한 연산을 지원하기 위해 여러 하드웨어 모듈이 집약된 복합체입니다. 주요 구성 요소는 다음과 같습니다.

1.  **Status register:** 연산 결과의 상태(Flag)를 저장합니다. 예를 들어 결과가 0인지(Zero), 음수인지(Negative), 혹은 계산 범위를 초과했는지(Overflow) 등을 비트로 기록합니다.
2.  **2’s complementer:** 컴퓨터는 뺄셈을 수행할 때 가산기(Adder)를 그대로 사용하기 위해 음수를 2의 보수 형태로 변환합니다. 이 장치는 음수 연산을 위한 보수 생성을 담당합니다.
3.  **Arithmetic operator:** 사칙연산($+, -, \times, \div$)을 수행하는 산술 연산자입니다.
4.  **Logic operator:** AND, OR, NOT, XOR 등 비트 단위의 논리 연산을 수행합니다.
5.  **Shift register:** 데이터를 왼쪽이나 오른쪽으로 한 비트씩 이동시키는 역할을 하며, 이는 곱셈이나 나눗셈의 고속 처리에 필수적입니다.

### Slide 47: ALU의 물리적 연산 동작 흐름
슬라이드의 다이어그램(그림 3-5)은 8비트 데이터 버스를 기반으로 한 ALU의 내부 동작 구조를 보여줍니다.

연산은 크게 세 단계로 진행됩니다.
1.  **데이터 공급:** 범용 레지스터에 있던 데이터가 8비트 데이터 버스를 타고 임시 레지스터인 **TEMP1(AC)**과 **TEMP2(B)**에 안착합니다.
2.  **연산 수행:** ALU는 두 임시 레지스터의 값을 입력받아 실제 연산(예: $AC + B$)을 수행합니다. 이때 연산 결과의 특징은 **상태(flag)** 신호로 빠져나가 상태 레지스터에 반영됩니다.
3.  **결과 저장:** 연산 결과는 다시 데이터 버스를 통해 누산기(AC)나 다른 범용 레지스터로 전송되어 저장됩니다($AC \leftarrow AC + B$).

이 과정은 제어 장치가 보내는 타이밍 신호에 맞춰 정교하게 이루어지며, CPU 내부 버스의 폭이 한 번에 처리할 수 있는 데이터의 크기를 결정합니다.

### Slide 48: 명령어 집합 구조(ISA) 단원의 시작
이제 컴퓨터 구조론의 가장 핵심적인 주제인 **명령어 집합 구조(Instruction Set Architecture, ISA)**에 대해 알아보겠습니다. 특히 현대 CPU 설계의 두 가지 큰 흐름인 **CISC(Complex Instruction Set Computer)**와 **RISC(Reduced Instruction Set Computer)**의 철학적 차이를 분석하는 것이 이 단원의 목표입니다.

ISA는 소프트웨어 개발자와 하드웨어 설계자 사이의 '약속'입니다. 소프트웨어는 하드웨어가 어떤 명령어를 알아듣는지 알아야 하고, 하드웨어는 그 명령어를 어떻게 물리적으로 실행할지 결정해야 합니다. 이 단원을 통해 우리가 작성한 고급 언어 코드가 어떻게 기계의 언어로 바뀌어 실행되는지 그 본질을 이해하게 될 것입니다.

### Slide 49: 프로그램 실행을 위한 추상화 계층
우리가 작성한 프로그램이 실제로 하드웨어에서 돌아가기까지는 수많은 추상화 계층을 거칩니다. 슬라이드의 구조도를 보면 큰 흐름을 알 수 있습니다.

*   **소프트웨어 계층:** 응용 프로그램에서 시작하여 알고리즘, 프로그래밍 언어(C 등), 그리고 이를 번역하는 컴파일러와 라이브러리를 거쳐 운영체제(OS)까지 내려옵니다.
*   **하드웨어 계층:** 가장 밑바닥의 물리/화학적 특성에서 시작하여 트랜지스터, 디지털 논리 회로, 그리고 하드웨어 기술 언어(HDL)로 설계된 구조까지 올라옵니다.

여기서 가운데의 **물음표(?)** 부분이 바로 이번 단원의 주인공인 **아키텍처(Architecture)**입니다. 소프트웨어 세계의 요구사항을 하드웨어 세계의 물리적 동작으로 연결해주는 유일한 다리가 바로 ISA입니다. 이 다리가 어떻게 설계되느냐에 따라 전체 시스템의 효율성이 결정됩니다.

### Slide 50: ISA의 정의: 하드웨어와 소프트웨어의 인터페이스
ISA는 단순히 명령어의 나열이 아니라, **소프트웨어에 노출되는 하드웨어의 추상화된 모습**입니다. 

1.  **인터페이스 역할:** 운영체제나 컴파일러를 만드는 소프트웨어 개발자에게 필요한 하드웨어 정보(명령어 종류, 레지스터 개수, 데이터 타입, 주소 지정 방식 등)를 문서화한 것입니다.
2.  **호환성:** 예를 들어 모든 64비트 인텔 CPU는 내부 설계(마이크로아키텍처)가 조금씩 달라도 동일한 **x86-64 ISA**를 따르기 때문에, 하나의 프로그램이 여러 종류의 인텔 CPU에서 문제없이 돌아갈 수 있습니다.
3.  **블랙박스(Black box) 개념:** 소프트웨어 개발자에게 하드웨어 내부의 복잡한 회로는 블랙박스입니다. 개발자는 ISA라는 매뉴얼만 보고 코드를 짭니다. 반대로 하드웨어 개발자는 ISA라는 목표를 달성하기 위해 최적의 마이크로아키텍처를 설계합니다.

결국 ISA는 하드웨어와 소프트웨어가 서로의 내부 사정을 몰라도 협업할 수 있게 해주는 공통 규격입니다.

## 설계 철학의 비교: CISC vs. RISC (Slides 51-60)

### Slide 51: ISA의 분류와 RISC-V 레지스터 구성
명령어 집합 구조(ISA)를 분류할 때 가장 핵심적인 기준은 내부 저장소의 형태와 데이터를 다루는 방식입니다. 현대 CPU는 대부분 범용 레지스터(General-purpose registers)를 사용하며, 데이터를 다루는 방식에 따라 '레지스터-메모리' 구조와 '로드-스토어' 구조로 나뉩니다.

현대적 RISC 설계의 대표 주자인 **RISC-V** 아키텍처는 전형적인 **로드-스토어(Load-store)** 구조를 채택하고 있습니다. 이는 산술 연산이 오직 레지스터 사이에서만 일어나며, 메모리에 접근하기 위해서는 반드시 별도의 '로드'나 '스토어' 명령어를 사용해야 함을 의미합니다. RISC-V의 기본적인 레지스터 세트는 다음과 같이 구성됩니다.
*   **32개의 정수 레지스터(General-purpose, g.p.):** 정수 연산과 주소 계산에 사용됩니다.
*   **32개의 부동 소수점 레지스터(Floating-point, f.p.):** 실수 연산을 위한 별도의 저장 공간입니다.

이러한 명확한 레지스터 분리는 컴파일러가 자원을 효율적으로 할당하고 하드웨어가 연산을 병렬로 처리하기 쉽게 만듭니다.

### Slide 52: ISA의 세부 속성: 주소 지정, 연산 및 인코딩
ISA를 정의하는 구체적인 결정 사항들을 살펴봅니다. 각 항목은 하드웨어 복잡도와 소프트웨어 효율성 사이의 균형점을 보여줍니다.

1.  **메모리 주소 지정(Memory addressing):** RISC-V는 바이트 단위 주소 지정(Byte addressed) 방식을 사용하며, 데이터가 정렬(Aligned)되어 있을 때 훨씬 빠른 접근 속도를 보장합니다.
2.  **주소 지정 모드(Addressing modes):** 데이터를 어디서 가져올지 결정하는 방식입니다. RISC-V는 레지스터(Register), 즉시값(Immediate), 변위(Displacement, $base + offset$) 모드와 같이 단순한 형태를 선호합니다. 반면 x86 같은 구조는 자동 증가(Autoincrement)나 인덱스(Indexed) 등 더 복잡한 모드를 지원하기도 합니다.
3.  **피연산자의 타입과 크기:** RISC-V는 기본적으로 8비트, 32비트, 64비트 크기의 데이터를 지원합니다.
4.  **제어 흐름 명령어(Control flow):** 함수 호출 후 돌아올 주소를 레지스터에 저장(RISC-V, ARM)할 것인지, 아니면 스택 메모리에 저장(x86)할 것인지 결정합니다.
5.  **명령어 인코딩(Encoding):** 모든 명령어의 길이를 일정하게 고정(Fixed length, RISC-V)하면 하드웨어 해석이 빨라집니다. 반면 명령어마다 길이를 다르게 설정(Variable length, x86)하면 코드 크기를 줄일 수 있습니다.

### Slide 53: RISC-V 명령어 사례 1 (데이터 이동 및 산술 연산)
교재의 그림 1.5를 통해 RISC-V 명령어가 실제 어떻게 구성되는지 구체적으로 확인해 보겠습니다.

*   **데이터 이동(Data transfers):** 메모리와 레지스터 사이의 통로입니다. `lb`(load byte)는 8비트, `lw`(load word)는 32비트 데이터를 메모리에서 읽어 레지스터에 넣습니다. `sd`(store double word)는 64비트 레지스터 값을 메모리에 저장합니다. 
*   **산술 및 논리 연산(Arithmetic/logical):** 정수 데이터를 가공합니다. `add`, `sub`는 기본 덧셈과 뺄셈이며, `addi`처럼 끝에 `i`가 붙은 명령어는 상수(Immediate)와 직접 연산합니다. `mul`과 `div`는 곱셈과 나눗셈을 담당하며, `and`, `or`, `xor` 같은 논리 연산도 포함됩니다.

중요한 점은 이 연산 명령어들이 오직 레지스터 값들만을 대상으로 작동한다는 것입니다. 메모리에 있는 값을 더하고 싶다면 반드시 `load`로 가져온 뒤 `add`를 수행해야 합니다.

### Slide 54: RISC-V 명령어 사례 2 (제어 및 부동 소수점 연산)
프로그램의 실행 흐름을 바꾸거나 복잡한 계산을 수행하는 명령어들입니다.

*   **제어(Control) 명령어:** 조건문이나 반복문을 구현합니다. `beq`(branch if equal)는 두 레지스터 값이 같으면 지정된 위치로 점프합니다. `jal`(jump and link)은 함수 호출 시 사용되며, 다음 실행 주소를 저장하고 목표 주소로 이동합니다.
*   **시스템 호출:** `ecall`은 운영체제(OS)에 특정 서비스를 요청할 때 사용하며, `ebreak`는 디버거가 실행을 멈추게 할 때 쓰입니다.
*   **부동 소수점(Floating point):** 실수 계산을 담당합니다. `fadd.d`, `fsub.s` 등은 각각 배정밀도(Double precision)와 단정밀도(Single precision) 실수를 연산합니다. `fsqrt`는 제곱근을 구하며, `fmax`나 `fmin`으로 두 값 중 큰 값이나 작은 값을 선택할 수도 있습니다.

이처럼 세분화된 명령어들은 하드웨어가 각 연산 유닛을 최적으로 설계할 수 있게 돕습니다.

### Slide 55: CISC(Complex Instruction Set Computers)의 철학
이제 대조적인 설계 방식인 **CISC**에 대해 알아봅니다. CISC는 RISC가 등장하기 이전의 주류 철학으로, 오늘날 인텔 x86 프로세서의 근간이 됩니다.

*   **설계 목표:** "가능한 한 적은 줄의 어셈블리 코드로 작업을 완료하는 것"입니다. 당시에는 메모리(RAM)가 매우 비싸고 귀했기 때문에 코드의 크기를 최소화하는 것이 지상 과제였습니다.
*   **하드웨어 중심 설계:** 복잡한 작업을 하나의 명령어로 처리하기 위해 프로세서 하드웨어를 복잡하게 설계했습니다.
*   **사례:** `MULT 2:3, 5:2`라는 가상의 명령어는 메모리 위치 $2:3$의 값과 $5:2$의 값을 곱해서 다시 메모리에 저장하는 모든 과정을 한 명령어로 끝냅니다. 프로그래머가 별도로 `load`나 `store`를 호출할 필요가 없는 '복잡한(Complex)' 명령어입니다.
*   **장점:** 
    1. 코드 길이가 짧아 메모리를 매우 적게 차지합니다.
    2. 컴파일러가 고수준 언어를 어셈블리로 번역할 때 할 일이 적어 설계가 비교적 단순해집니다.

CISC는 하드웨어가 소프트웨어의 고생을 대신 짊어지는 구조라고 이해할 수 있습니다.

### Slide 56: RISC(Reduced Instruction Set Computers)의 철학
CISC의 복잡함에 대항하여 등장한 설계 철학이 바로 **RISC**입니다. RISC는 "단순한 것이 강력하다"는 원칙에 기반합니다.

*   **설계 목표:** 명령어를 단순화하여 모든 명령어가 **하나의 클럭 사이클(One clock cycle)** 이내에 실행되도록 하는 것입니다. 
*   **명령어의 분해:** CISC에서 하나의 명령어였던 `MULT`를 RISC에서는 `LOAD`, `PROD`(곱셈), `STORE`라는 세 개의 단순한 명령어로 나누어 처리합니다. 
    *   `LOAD A, 2:3`: 메모리에서 값을 가져옴
    *   `LOAD B, 5:2`: 또 다른 값을 가져옴
    *   `PROD A, B`: 레지스터끼리 곱함
    *   `STORE 2:3, A`: 결과를 메모리에 저장
*   **장점:**
    1. 하드웨어 설계에 필요한 트랜지스터 수를 대폭 줄여 공간 효율성을 높입니다.
    2. 모든 명령어의 실행 시간이 일정하기 때문에, 여러 명령어를 겹쳐서 실행하는 **파이프라이닝(Pipelining)** 기술을 적용하기에 매우 유리합니다.
    3. 결과적으로 복잡한 명령어 하나를 수행하는 시간과 단순한 명령어 여러 개를 수행하는 전체 시간이 거의 비슷해지거나, 오히려 RISC가 더 빨라집니다.

### Slide 57: CISC와 RISC의 상세 비교 및 효율성 분석
두 아키텍처의 차이점을 표와 함께 심층적으로 비교해 보겠습니다.

| 구분 | CISC | RISC |
| :--- | :--- | :--- |
| **강조점** | 하드웨어 (복잡한 회로) | 소프트웨어 (효율적 컴파일) |
| **명령어 특징** | 여러 사이클 소요, 복잡함 | 단일 사이클 소요, 단순함 |
| **메모리 접근** | 메모리 간 직접 연산 가능 | 레지스터 간 연산만 가능 (Load-Store) |
| **코드 특징** | 작은 코드 크기, 높은 CPI | 큰 코드 크기, 낮은 CPI |
| **트랜지스터 활용** | 복잡한 명령어 제어 회로에 사용 | 더 많은 범용 레지스터 구현에 사용 |

여기서 주목할 점은 **레지스터의 활용**입니다. CISC의 `MULT` 명령어는 연산이 끝나면 레지스터의 값을 지워버리는 경우가 많아, 동일한 데이터를 다시 쓸 때 메모리에서 또 읽어와야 합니다. 반면 RISC는 데이터를 레지스터에 명시적으로 로드해 두기 때문에, 다른 값이 덮어씌워지기 전까지 해당 데이터를 **재사용**할 수 있습니다. 이는 결과적으로 불필요한 메모리 접근(Traffic)을 줄여 전체적인 시스템 부하를 감소시킵니다.

### Slide 58: 시장의 현황과 두 아키텍처의 융합
전통적으로 CISC와 RISC는 서로 다른 영역에서 발전해 왔으나, 최근에는 그 경계가 점차 모호해지고 있습니다.

1.  **대표적인 프로세서:**
    *   **CISC:** 인텔의 x86 라인업이 대표적입니다. 호환성과 유연성이 뛰어나지만 전력 소모가 큽니다.
    *   **RISC:** 스마트폰의 ARM, 애플의 M1, MIPS 등이 대표적입니다. 저전력 설계에 최적화되어 임베디드 장치에 주로 쓰입니다.
2.  **기술의 융합:** 최근에는 "CISC냐 RISC냐"를 나누는 것이 큰 의미가 없어졌습니다.
    *   **인텔(CISC)의 변화:** 외부적으로는 CISC 명령어를 받아들이지만, CPU 내부 하드웨어가 이를 RISC 형태의 작은 단위(Micro-ops)로 쪼개어 처리함으로써 RISC의 성능적 장점을 흡수했습니다.
    *   **ARM(RISC)의 변화:** 모바일 시장을 넘어 고성능 서버나 PC 시장으로 진출하면서, 복잡한 연산을 효율적으로 처리하기 위해 CISC적인 요소들을 도입하며 진화하고 있습니다.

### Slide 59: 현대적 RISC의 표준: RISC-V
2010년 UC 버클리에서 개발된 **RISC-V**는 현대적인 RISC 설계의 결정체입니다.

*   **오픈 소스:** 누구나 무료로 사용할 수 있는 공개 표준 ISA입니다. 특정 기업에 종속되지 않아 전 세계적으로 급격히 확산되고 있습니다.
*   **설계 특징:** 과거 RISC 설계들의 장점은 계승하고 단점은 버렸습니다. 
    *   매우 많은 수의 레지스터 세트를 제공합니다.
    *   파이프라이닝이 매우 용이하도록 명령어를 설계했습니다.
    *   군더더기 없는 최소한의 연산 세트(Lean set of operations)를 지향합니다.
*   **생태계:** 현재 RISC-V 재단을 통해 구글, 삼성, NVIDIA, 퀄컴 등 글로벌 IT 기업들이 주도적으로 개발 및 유지보수에 참여하고 있습니다. 이는 미래 컴퓨팅 환경에서 RISC-V가 핵심적인 역할을 할 것임을 시사합니다.

### Slide 60: 컴퓨터 아키텍처의 현대적 정의
강의를 마무리하며 '컴퓨터 아키텍처'라는 개념을 다시 정의합니다. 시대에 따라 아키텍처를 바라보는 관점은 변해왔습니다.

1.  **과거의 관점 (Old view):** 주로 **명령어 집합 구조(ISA) 설계** 자체에 집중했습니다. 레지스터를 몇 개 둘 것인지, 주소 지정 방식은 무엇으로 할 것인지 등 '소프트웨어가 보는 하드웨어의 모습'을 결정하는 것이 주된 업무였습니다.
2.  **현대적 관점 (Real computer architecture):** 단순한 사양 결정을 넘어, 특정 목표(Target machine)의 요구사항을 만족시키기 위한 **전체적인 최적화**를 의미합니다.
    *   **제약 조건 내 성능 극대화:** 비용(Cost), 전력 소모(Power), 가용성(Availability)이라는 현실적인 제약 안에서 최고의 성능을 뽑아내는 설계입니다.
    *   **포함 범위:** 이제 아키텍처는 **ISA**뿐만 아니라, 이를 실제로 구현하는 **마이크로아키텍처(Microarchitecture)**와 물리적인 **하드웨어** 전체를 아우르는 통합적인 설계 예술로 정의됩니다.


## 피연산자 위치에 따른 ISA 분류 (Slides 61-66)

### Slide 61: 컴퓨터 시스템의 추상화 계층과 아키텍처의 위치
컴퓨터 시스템은 복잡한 하드웨어를 효율적으로 제어하기 위해 여러 단계의 추상화 계층으로 이루어져 있습니다. 이 슬라이드는 최상위의 응용 프로그램부터 최하위의 물리 법칙까지의 전체 계층 구조를 보여줍니다.

가장 중요한 지점은 빨간색 박스로 표시된 **아키텍처(Architecture)** 부분입니다. 아키텍처는 소프트웨어 계층(컴파일러, OS 등)과 하드웨어 계층(마이크로아키텍처, 회로 등)이 만나는 **유일한 접점(Interface)**입니다. 소프트웨어는 하드웨어가 어떤 물리적 구조로 이루어져 있는지 몰라도 아키텍처가 제공하는 명령어 규칙만 알면 프로그램을 실행할 수 있습니다. 반대로 하드웨어는 아키텍처가 약속한 명령어들을 정확하게 수행하기만 하면 어떤 소프트웨어도 구동할 수 있습니다. 즉, 아키텍처는 복잡한 시스템을 두 세계로 나누어 독립적으로 발전하게 만드는 '추상화의 핵심'입니다.

### Slide 62: 명령어 집합 구조의 분류 기준
이제 구체적으로 ISA를 어떻게 분류하는지 알아보겠습니다. 이 내용은 컴퓨터 구조론의 고전인 *Computer Architecture: A Quantitative Approach (CA book)*의 부록 A.2 내용을 바탕으로 합니다.

ISA를 분류하는 가장 보편적인 방법은 **'명령어가 사용하는 피연산자(Operand)가 프로세서 내부의 어디에 저장되는가'**를 확인하는 것입니다. 피연산자의 위치에 따라 연산 방식과 하드웨어 구조가 완전히 달라지기 때문입니다. 다음 슬라이드부터 프로세서 내부 저장소의 유형에 따른 구체적인 분류법을 살펴보겠습니다.

### Slide 63: 내부 저장소 유형에 따른 분류와 명시성
프로세서 내부에서 데이터를 일시적으로 보관하는 장소의 유형에 따라 아키텍처를 세 가지로 분류할 수 있습니다.

1.  **스택(Stack) 아키텍처:** 데이터가 LIFO(Last-In-First-Out) 구조의 스택에 저장됩니다.
2.  **누산기(Accumulator) 아키텍처:** 하나의 특수 레지스터(누산기)에 연산 결과가 항상 저장됩니다.
3.  **범용 레지스터(GPR) 아키텍처:** 여러 개의 레지스터를 자유롭게 사용하여 데이터를 저장합니다.

여기서 중요한 개념은 **암시적(Implicit)**과 **명시적(Explicit)**의 차이입니다. 스택이나 누산기 방식은 연산 대상이 이미 정해져 있어 명령어에 피연산자 위치를 적지 않아도 되는 '암시적' 방식을 취합니다. 반면 GPR 방식은 어떤 레지스터를 쓸지 명령어에 직접 적어주는 '명시적' 방식을 사용합니다. 1980년대 이전의 초기 컴퓨터들은 주로 스택이나 누산기 방식을 사용했으나, 현대 컴퓨터는 대부분 GPR 방식을 채택하고 있습니다.

### Slide 64: 산술 연산 $C = A + B$ 구현 방식 비교
네 가지 서로 다른 아키텍처 스타일에서 $C = A + B$라는 동일한 연산이 어떻게 코드로 구현되는지 비교해 보겠습니다.

*   **스택 (Stack):** `Push A`, `Push B` 후 `Add`를 하면 스택 상단의 두 값을 더해 다시 스택에 넣습니다. 피연산자가 스택 상단으로 **암시적**입니다.
*   **누산기 (Accumulator):** `Load A`로 누산기에 값을 넣고 `Add B`를 하면 누산기 값과 B를 더합니다. 결과는 **암시적**으로 다시 누산기에 저장됩니다.
*   **레지스터-메모리 (Register-memory):** `Add R3, R1, B`처럼 레지스터와 메모리 주소를 **명시적**으로 섞어서 연산할 수 있습니다.
*   **로드-스토어 (Load-store):** 모든 값을 레지스터로 가져온 뒤(`Load R1, A`, `Load R2, B`), 오직 레지스터끼리만 연산합니다(`Add R3, R1, R2`). 모든 피연산자 위치를 **명시적**으로 지정해야 합니다.

그림에서 보듯이 오른쪽으로 갈수록 피연산자를 명시하는 정도가 높아지며, 현대적인 RISC는 가장 오른쪽의 로드-스토어 방식을 사용합니다.

### Slide 65: 현대 컴퓨터가 로드-스토어(Load-store) 방식을 쓰는 이유
오늘날 대부분의 고성능 프로세서가 로드-스토어 아키텍처를 채택하는 데에는 명확한 성능상의 이유가 있습니다.

1.  **속도:** 레지스터는 메인 메모리(RAM)보다 물리적으로 훨씬 가깝고 빠릅니다.
2.  **컴파일러 효율성:** 컴파일러 입장에서 여러 개의 범용 레지스터를 활용하는 것이 스택이나 누산기보다 식을 최적화하기에 훨씬 유리합니다.
3.  **메모리 트래픽 감소:** 자주 쓰는 변수를 레지스터에 계속 담아두고 재사용할 수 있어, 느린 메모리에 접근하는 횟수를 줄일 수 있습니다.
4.  **코드 밀도와 성능:** 레지스터는 주소값보다 훨씬 적은 비트수로 이름을 붙일 수 있어 명령어 구성을 효율적으로 만들 수 있고, 결과적으로 프로그램 전체의 실행 속도를 높입니다.

이러한 장점들 덕분에 로드-스토어 방식은 파이프라이닝과 같은 현대적 CPU 고속화 기술을 적용하기에 가장 적합한 구조가 되었습니다.

### Slide 66: GPR 아키텍처의 세부 특성과 분류
범용 레지스터(GPR)를 사용하는 아키텍처 내에서도 두 가지 세부 속성에 따라 유형이 나뉩니다.

첫째는 **피연산자의 개수**입니다. 결과값과 소스값 하나를 공유하는 '2-피연산자' 형식(예: $R1 = R1 + R2$)과, 결과값과 두 소스값을 모두 따로 지정하는 '3-피연산자' 형식(예: $R3 = R1 + R2$)이 있습니다.
둘째는 **메모리 주소의 개수**입니다. 한 명령어 내에서 메모리 주소를 몇 개나 참조할 수 있는지를 나타냅니다.

*   **로드-스토어 (0, 3):** 연산 시 메모리 주소를 0개 참조(모두 레지스터)하며, 3-피연산자 형식을 씁니다. (예: ARM, RISC-V)
*   **레지스터-메모리 (1, 2):** 메모리 주소 1개와 레지스터를 섞어 쓰며, 2-피연산자 형식을 씁니다. (예: Intel x86)
*   **메모리-메모리 (2, 2) 또는 (3, 3):** 명령어 하나가 메모리 주소만으로 연산할 수 있는 매우 복잡한 방식입니다. (예: VAX)

하단 표는 이러한 조합에 따른 대표적인 아키텍처 예시들을 보여주며, 설계의 복잡도와 유연성이 어떻게 트레이드 오프(Trade-off)되는지 설명합니다.

## 메모리 접근 방식: Load-Store 구조의 이해 (Slides 67-69)

### Slide 67: ISA 유형별 장단점 비교와 설계 전략
명령어 집합 구조의 설계 방식에 따른 장단점은 절대적이지 않으며, 컴파일러의 기술력과 구체적인 구현 전략에 따라 그 영향이 달라집니다. 슬라이드의 표를 통해 세 가지 주요 유형을 비교해 보겠습니다.

1.  **레지스터-레지스터 (Load-Store) 방식 (0, 3):**
    *   **장점:** 명령어 인코딩이 고정 길이로 매우 단순하여 하드웨어 구현이 쉽습니다. 모델이 단순하여 컴파일러가 코드를 생성하기 용이하며, 대부분의 명령어가 비슷한 클럭 사이클 내에 실행됩니다.
    *   **단점:** 모든 메모리 접근을 별도의 명령어로 처리해야 하므로, 다른 방식에 비해 전체 명령어 개수(Instruction Count)가 늘어납니다. 이는 프로그램 크기를 키우고 명령어 캐시 효율에 영향을 줄 수 있습니다.
2.  **레지스터-메모리 방식 (1, 2):**
    *   **장점:** 별도의 로드 명령어 없이 연산과 동시에 메모리 데이터를 참조할 수 있어 코드 밀도가 좋습니다.
    *   **단점:** 연산 시 소스 피연산자 중 하나가 결과값으로 덮어씌워져 파괴됩니다. 또한, 레지스터 번호와 메모리 주소의 비트 수가 달라 명령어 인코딩이 복잡해지며, 연산마다 클럭 사이클이 달라질 수 있습니다.
3.  **메모리-메모리 방식 (2, 2) 또는 (3, 3):**
    *   **장점:** 가장 간결한 코드를 생성하며 중간 값을 저장하기 위한 레지스터 낭비가 없습니다.
    *   **단점:** 명령어 크기의 변동이 매우 심하고, 명령어 하나가 수행하는 작업량이 너무 많아 하드웨어 설계가 극도로 복잡해집니다. 메모리 병목 현상의 주범이 되므로 현대 컴퓨터에서는 더 이상 사용되지 않습니다.

### Slide 68: 로드-스토어(Load-Store) 아키텍처의 데이터 흐름
이 다이어그램은 현대 컴퓨터의 표준인 로드-스토어 구조에서 데이터가 프로세서와 메모리 사이를 어떻게 이동하는지 시각적으로 보여줍니다.

*   **프로세서(Processor) 내부:** 제어 장치(Control)와 데이터패스(Datapath)로 구성됩니다. 데이터패스 안에는 다음에 실행할 주소를 가리키는 **PC**, 연산의 핵심인 **ALU**, 그리고 데이터를 보관하는 **레지스터(Registers)**가 있습니다. 레지스터는 속도가 매우 빠르지만 공간이 한정적이라는 특징이 있습니다.
*   **메모리(Memory) 외부:** 프로그램 코드(Text)와 실제 데이터(Data)가 저장됩니다. 레지스터에 비해 공간은 훨씬 넓지만 속도는 상대적으로 매우 느립니다.
*   **핵심 동작:** 
    1.  **Load:** 메모리의 Data 영역에서 레지스터로 데이터를 읽어옵니다(Read data).
    2.  **Store:** ALU 연산이 끝난 레지스터의 결과값을 다시 메모리로 저장합니다(Write data).
    3.  **Fetch:** 메모리의 Text 영역에서 실행할 명령어를 가져옵니다(Fetch instruction).

중요한 원칙은 **"모든 산술 및 논리 연산은 반드시 레지스터 안에서만 일어난다"**는 것입니다. 이 구조 덕분에 하드웨어는 복잡한 메모리 연산을 고민할 필요 없이, 레지스터와 ALU 사이의 고속 연산에만 집중할 수 있습니다.

### Slide 69: 강의 마무리 및 요약
이번 장에서는 컴퓨터 아키텍처의 핵심 요소인 성능 측정법, CPU의 물리적 구성, 그리고 하드웨어와 소프트웨어의 가교 역할을 하는 ISA(명령어 집합 구조)에 대해 학습했습니다.

우리는 왜 현대 컴퓨터가 단순한 RISC 구조와 로드-스토어 방식을 선호하는지, 그리고 이러한 설계가 어떻게 전체적인 시스템 성능 향상으로 이어지는지 분석했습니다. 성능은 단순히 클럭 주파수 하나로 결정되는 것이 아니라, 명령어 개수와 CPI, 그리고 클럭 주기가 유기적으로 결합된 결과물임을 이해하는 것이 중요합니다. 

이것으로 성능(Performance), CPU, ISA에 관한 강의를 마치겠습니다. 수고하셨습니다.
