# 대주제 1. RISC-V 프로시저 호출 및 레지스터 관리 (Slide 3~20)

## 1.1 프로시저 호출의 기본 원리와 규약 (Slide 3~6)

프로그램이 복잡해짐에 따라 코드를 재사용하고 구조화하기 위해 `Procedure`(프로시저) 혹은 `Function`(함수)의 개념이 필요합니다. 이 섹션에서는 프로시저가 호출되고 반환되는 하드웨어적인 메커니즘과 RISC-V에서 정의한 규약을 다룹니다.

### Slide 3: Procedure (ch. 2.8, COD book)
프로시저 호출에 관한 내용은 'Computer Organization and Design (COD)' 교재의 2.8 절을 바탕으로 합니다. 프로시저는 특정 작업을 수행하기 위해 따로 분리된 `subroutine`을 의미하며, 소프트웨어 개발에서 `Abstraction`(추상화)을 실현하는 핵심 도구입니다.

### Slide 4: Procedure (or function)
`Procedure`(프로시저)는 프로그래밍 언어에서 함수(Function)나 서브루틴(Subroutine)이라고도 불리며, 특정 작업을 수행하기 위해 별도로 분리된 코드 뭉치를 의미합니다. 우리가 프로그램을 작성할 때 모든 코드를 한 줄로 길게 늘어놓지 않고 기능별로 쪼개어 관리하는 이유는 크게 두 가지입니다. 첫째는 코드의 재사용성입니다. 똑같은 연산이 여러 번 필요할 때 매번 새로 작성하지 않고 이미 만들어진 프로시저를 호출하기만 하면 됩니다. 둘째는 `Abstraction`(추상화)입니다. 내부의 복잡한 구현 과정을 몰라도 함수 이름과 매개변수($Parameters$)만 알면 그 기능을 사용할 수 있게 되어 전체 프로그램을 이해하기 훨씬 쉬워집니다.

### Slide 5: Procedure call - Steps required
프로시저가 호출되고 실행된 뒤 다시 돌아오는 과정은 단순히 점프하는 것보다 훨씬 복잡한 조율이 필요합니다. 이를 위해 RISC-V에서는 호출하는 쪽인 `caller`(호출자)와 호출을 당하는 쪽인 `callee`(피호출자)가 지켜야 할 7가지 필수 단계를 규정하고 있습니다.

**1~2단계: caller(호출자)의 준비**
1.  **인자 배치**: 프로시저가 작업에 필요한 재료인 인자($Arguments$)를 약속된 장소인 레지스터 $x10$ ~ $x17$에 넣습니다. 프로시저는 이 레지스터들을 통해 필요한 데이터를 전달받습니다.
2.  **제어권 전송**: 프로그램의 실행 흐름을 프로시저가 시작되는 지점으로 옮깁니다.

**3~6단계: callee(피호출자)의 실행**
3.  **자원 확보**: 프로시저가 연산 과정에서 사용할 임시 저장 공간(메모리 리소스 등)을 확보합니다.
4.  **작업 수행**: 프로시저 내부에 작성된 실제 기능을 실행합니다.
5.  **결과 배치**: 계산이 끝나면 그 결과값을 다시 $x10$ ~ $x17$ 중 하나에 넣어 호출자가 확인할 수 있게 합니다.
6.  **상태 복구**: 프로시저가 실행되면서 변경했던 레지스터 값들을 원래대로 되돌리고, 사용했던 로컬 저장 공간을 해제하여 호출 전의 상태로 복원합니다.

**7단계: 복귀**
7.  **제어권 반환**: 작업을 모두 마쳤으므로, 원래 호출되었던 지점(레지스터 $x1$에 저장된 주소)으로 돌아가 메인 프로그램의 다음 코드를 실행하게 합니다.

이처럼 하드웨어는 정해진 규칙에 따라 레지스터와 메모리를 관리하며 프로시저를 안전하게 실행합니다. 특히 인자 전달과 결과 반환에 동일한 레지스터 영역($x10$ ~ $x17$)을 사용하는 점이 효율적입니다.

**7단계: 복귀**
7.  원래 호출되었던 지점(레지스터 $x1$에 저장된 주소)으로 제어권을 반환합니다.

### Slide 6: RISC-V procedure call

앞서 살펴본 프로시저 호출의 7단계 과정을 실제로 구현하기 위해, RISC-V는 레지스터 사용에 대한 약속인 `convention`(관례)과 두 가지 핵심 명령어를 제공합니다. 하드웨어 수준에서 데이터가 어떻게 오고 가는지 구체적으로 살펴보겠습니다.

**1. RISC-V 레지스터 사용 규칙**
*   **$x10$ ~ $x17$ (8개의 파라미터 레지스터)**: 프로시저를 호출할 때 필요한 인자($Arguments$)를 넘겨주거나, 작업을 마친 후 결과($Return values$)를 받아올 때 사용합니다. 별도의 메모리 접근 없이 레지스터를 직접 사용하므로 속도가 매우 빠릅니다.
*   **$x1$ (리턴 어드레스 레지스터)**: 프로시저가 끝난 뒤 다시 돌아갈 '복귀 주소'를 저장하는 전용 레지스터입니다.

**2. 프로시저 호출: `jal` (Jump and Link)**
*   명령어 형식: `jal x1, procedureLabel`
*   **동작**: 프로그램의 실행 위치를 `procedureLabel`로 옮김(Jump)과 동시에, 현재 명령어 바로 다음 주소($PC+4$)를 $x1$ 레지스터에 기록(Link)합니다. 여기서 'Link'라는 표현은 나중에 돌아올 길을 연결해 둔다는 의미로 이해하면 쉽습니다.

**3. 프로시저 반환: `jalr` (Jump and Link Return)**
*   명령어 형식: `jalr x0, 0(x1)`
*   **동작**: $x1$ 레지스터에 저장된 주소로 다시 점프하여 복귀합니다. 
*   **특징**: 이때 대상 레지스터로 $x0$를 지정하는데, $x0$는 하드웨어적으로 항상 0이 저장되어 있어 값을 수정할 수 없는 레지스터입니다. 즉, 돌아갈 때는 어딘가에 주소를 새로 기록(Link)할 필요가 없으므로 기록할 대상인 $rd$ 자리에 $x0$를 넣어 그 결과를 무시하는 것입니다.

이처럼 `jal`과 `jalr`의 조합을 통해 함수를 부르고(Call), 원래 자리로 돌아오는(Return) 메커니즘이 완성됩니다.

## 1.2 스택(Stack) 활용과 리프(Leaf) 프로시저 (Slide 7~12)

프로시저에서 사용할 수 있는 인자 레지스터($x10$ ~ $x17$)는 8개로 한정되어 있습니다. 더 많은 레지스터가 필요하거나, 기존 레지스터의 값을 보존해야 할 때는 메모리의 특정 영역인 `Stack`(스택)을 활용합니다.

### Slide 7: RISC-V procedure call – Cont’d

우리가 앞서 배운 인자 전달용 레지스터($x10$ ~ $x17$)는 총 8개입니다. 하지만 복잡한 계산을 수행하는 프로시저라면 8개보다 더 많은 레지스터가 필요할 수도 있고, 혹은 기존에 다른 용도로 쓰이던 레지스터를 잠시 빌려 써야 할 상황도 생깁니다. 이때 발생하는 문제가 "기존 데이터를 어떻게 보호할 것인가?"입니다.

피호출자($Callee$)는 자신의 임무가 끝나고 호출자($Caller$)에게 제어권을 돌려주기 전에, **호출자가 원래 가지고 있던 레지스터 값들을 반드시 호출 전 상태로 복구**해 놓아야 합니다. 마치 남의 물건을 빌려 썼으면 제자리에 돌려놓아야 하는 것과 같습니다. 이렇게 레지스터의 데이터를 메모리의 특정 공간으로 잠시 대피시키는 과정을 레지스터를 메모리로 쏟아낸다는 의미에서 `Spilling registers`라고 부릅니다.

이 데이터를 안전하게 쌓아두기 위해 사용하는 자료구조가 바로 `stack`(스택)입니다.
*   **작동 방식**: 데이터를 넣는 것을 `Push`, 꺼내는 것을 `Pop`이라고 합니다. 가장 나중에 넣은 것을 가장 먼저 꺼내는 'Last In - First Out'(LIFO) 구조입니다.
*   **스택 포인터 ($sp$)**: 현재 스택의 최상단(데이터가 쌓여있는 지점)을 가리키는 포인터로, RISC-V에서는 **레지스터 $x2$**를 전용으로 사용합니다.
*   **성장 방향**: RISC-V에서 스택의 가장 중요한 특징은 **높은 주소에서 낮은 주소 방향으로 자라난다**는 점입니다. 
    *   따라서 데이터를 스택에 저장(`Push`)하려면 $sp$ 값에서 필요한 바이트만큼 숫자를 **빼서** 공간을 먼저 확보해야 합니다.
    *   반대로 데이터를 다 쓰고 복구(`Pop`)할 때는 $sp$ 값에 숫자를 **더해서** 공간을 비워주게 됩니다.

이처럼 스택은 레지스터라는 좁은 공간의 한계를 극복하고, 함수 간의 데이터를 안전하게 보존해 주는 '임시 보관소' 역할을 수행합니다.

### Slide 8: RISC-V procedure call – Cont’d (Example)

앞서 배운 스택의 원리를 실제 코드로 확인해 보겠습니다. 이번 예제는 다른 함수를 전혀 호출하지 않고 자기 할 일만 마치고 끝나는 `leaf procedure`(리프 프로시저)인 `leaf_example` 함수입니다. 나뭇가지의 맨 끝에 달린 잎사귀처럼 더 이상 뻗어 나가지 않는다는 의미에서 리프 프로시저라고 부릅니다.

**1. 예시 코드와 레지스터 할당**
*   **C 코드**: `f = (g + h) - (i + j)` 연산을 수행하고 결과를 반환합니다.
*   **가정 (Mapping)**: 
    *   매개변수 $g, h, i, j$는 각각 `argument registers`인 $x10, x11, x12, x13$에 들어있다고 가정합니다.
    *   결과값 $f$는 $x20$ 레지스터에 저장하기로 약속합니다.

**2. 추가 레지스터의 필요성**
이 수식을 계산하기 위해서는 중간 단계가 필요합니다. 
1.  먼저 $(g + h)$를 계산해서 어딘가에 두어야 합니다.
2.  그다음 $(i + j)$를 계산해서 또 어딘가에 두어야 합니다.
3.  마지막으로 두 값을 빼야 합니다.
이 중간 값들을 담아두기 위해 **임시 레지스터 $x5$와 $x6$**를 추가로 사용하기로 합니다.

**3. 왜 스택에 저장해야 하는가?**
여기서 핵심은 **$x20, x5, x6$ 레지스터는 원래 이 함수를 호출한 쪽(Caller)에서 다른 중요한 용도로 쓰고 있었을지도 모른다**는 점입니다. 함수가 이 레지스터들을 무턱대고 그냥 써버리면 호출한 쪽의 데이터가 지워져 프로그램이 망가질 수 있습니다. 

따라서 함수를 시작하자마자 이 **세 개의 레지스터($x20, x5, x6$) 값을 `stack`에 안전하게 대피(Save)**시켜야 합니다. 함수가 끝나기 직전에 다시 스택에서 꺼내 원래대로 돌려놓으면, 호출한 쪽은 자신의 레지스터 값이 변하지 않은 것처럼 안전하게 작업을 이어갈 수 있습니다.


### Slide 9: RISC-V procedure call – Cont’d (Assembly Code)

앞선 **Slide 8**에서 설계한 논리를 실제 RISC-V 어셈블리 코드로 구현한 모습입니다. 코드는 크게 준비($Prologue$), 연산($Body$), 복구($Epilogue$), 반환($Return$)의 4단계로 나뉩니다.

**1. 준비 단계 (Prologue)**
*   `addi sp, sp, -12`: 레지스터 3개를 저장하기 위해 `stack pointer`를 12바이트($3 \times 4$바이트)만큼 아래로 이동시켜 공간을 만듭니다.
*   `sw x5, 8(sp)`, `sw x6, 4(sp)`, `sw x20, 0(sp)`: 호출자가 쓰던 기존의 $x5, x6, x20$ 값을 스택의 빈 공간에 안전하게 저장(`Store Word`)합니다.

**2. 실제 연산 단계 (Body)**
*   `add x5, x10, x11`: 인자 $g, h$가 담긴 $x10, x11$을 더해 $x5$에 넣습니다.
*   `add x6, x12, x13`: 인자 $i, j$가 담긴 $x12, x13$을 더해 $x6$에 넣습니다.
*   `sub x20, x5, x6`: $(g+h) - (i+j)$를 수행하여 결과 $f$를 $x20$에 저장합니다.

**3. 결과값 전달 및 복구 단계 (Epilogue)**
*   `addi x10, x20, 0`: 계산 결과인 $x20$의 값을 리턴 전용 레지스터인 $x10$으로 복사합니다. ($x10$은 호출될 때 인자를 가져왔지만, 나갈 때는 결과값을 담아가는 역할을 겸합니다.)
*   `lw x20, 0(sp)`, `lw x6, 4(sp)`, `lw x5, 8(sp)`: 아까 스택에 치워두었던 호출자의 원래 레지스터 값들을 다시 읽어와서(`Load Word`) 복구합니다.
*   `addi sp, sp, 12`: 사용이 끝난 스택 공간을 반환하기 위해 `sp`를 다시 위로 올립니다.

**4. 호출 지점으로 복귀 (Return)**
*   `jalr x0, 0(x1)`: 호출자가 `jal` 명령어를 썼을 때 $x1$ 레지스터에 자동으로 저장해두었던 복귀 주소로 점프하여 돌아갑니다.

이 과정을 통해 함수는 자신의 작업을 완벽히 수행하면서도, 호출자의 레지스터 상태를 하나도 망가뜨리지 않고 복귀할 수 있게 됩니다.

### Slide 11: Local Data on the Stack – Cont’d

앞선 슬라이드들에서 스택의 동작을 배웠다면, 이번 장에서는 프로세서와 메모리의 전체적인 관계 속에서 왜 우리가 번거롭게 데이터를 주고받아야 하는지 그 근본적인 이유를 시각적으로 보여줍니다. 

**1. 프로세서와 메모리의 물리적 차이**
*   **프로세서 내부 (왼쪽)**: 데이터 처리를 직접 수행하는 곳입니다. 여기에는 `Registers`가 위치하며, 하드웨어적으로 프로세서와 가장 가까워 접근 속도가 매우 빠릅니다($Very\ fast$). 하지만 공간이 32개(RISC-V 기준)로 매우 한정적($limited\ space$)이라는 치명적인 단점이 있습니다.
*   **메모리 (오른쪽)**: 데이터 보관소입니다. `Stack`과 `Text` 영역 등이 여기에 위치합니다. 레지스터에 비해 훨씬 더 많은 데이터를 담을 수 있는 큰 공간($Much\ larger\ place$)을 제공하지만, 프로세서 외부에 있어 통신하는 데 시간이 걸리므로 속도가 레지스터보다 느립니다($slower\ than\ registers$).

**2. 데이터의 흐름과 순환**
*   **명령어 인출 (Fetch instruction)**: 프로세서는 메모리의 `Text` 세그먼트로부터 실행할 기계어 명령어를 가져와 `Control` 유닛으로 전달합니다.
*   **데이터 저장 (Store to memory)**: 연산 도중 레지스터 공간이 부족하거나 함수 호출로 데이터를 보존해야 할 때, `Write data` 신호와 함께 레지스터의 값을 메모리의 `Stack` 영역으로 보냅니다.
*   **데이터 읽기 (Load from memory)**: 메모리에 보관해 두었던 데이터가 다시 필요해지면 `Read data` 과정을 거쳐 레지스터로 다시 읽어옵니다.

**결론적으로**, 우리는 빠른 레지스터를 최대한 효율적으로 사용하되, 한계가 올 때만 느리지만 넓은 메모리(`Stack`)를 보조 저장소로 활용하는 전략을 취합니다. 이것이 바로 컴퓨터 시스템이 속도와 용량 사이에서 균형을 맞추는 핵심 원리입니다.

### Slide 12: RISC-V registers (ABI Convention)

앞선 **Slide 9**의 예제에서 우리는 $x5, x6, x20$ 세 개의 레지스터를 모두 스택에 저장했습니다. 하지만 매번 모든 레지스터를 메모리에 쓰고 읽는 것은 프로그램 속도를 매우 느리게 만듭니다. 이를 최적화하기 위해 RISC-V는 `ABI`(Application Binary Interface)라는 표준 규약을 정해, 어떤 레지스터를 누가 책임지고 보존할지 약속해 두었습니다. 이를 통해 불필요한 `register spilling`(레지스터 대피)을 줄일 수 있습니다.

**1. 보존 의무에 따른 레지스터 분류**
*   **임시 레지스터 (Temporary registers, $x5$ ~ $x7$, $x28$ ~ $x31$ / 별칭 `t0` ~ `t6`)**:
    *   이 레지스터들은 피호출자($Callee$)가 마음대로 사용하고 값을 바꿔도 됩니다. 호출자($Caller$)는 이 값이 함수 호출 후에도 유지될 것이라고 기대하지 않습니다. 따라서 피호출자는 이 레지스터들을 굳이 스택에 저장할 필요가 없습니다. (**Caller-saved**)
*   **저장 레지스터 (Saved registers, $x8$ ~ $x9$, $x18$ ~ $x27$ / 별칭 `s0` ~ `s11`)**:
    *   이 레지스터들은 매우 중요하므로 피호출자가 만약 사용하게 된다면, 반드시 원래 값을 스택에 보존했다가 함수가 끝나기 전에 복구해 주어야 합니다. (**Callee-saved**)

**2. 기타 주요 레지스터**
*   **$x1$ (`ra`)**: 리턴 주소 레지스터입니다. 호출자가 관리하지만, 중첩 호출 시엔 보존이 필요합니다.
*   **$x2$ (`sp`)**: 스택 포인터입니다. 함수 종료 시 반드시 원래 위치로 돌려놓아야 합니다.
*   **$x10$ ~ $x17$ (`a0` ~ `a7`)**: 인자 전달 및 결과 반환용입니다.

**3. 이전 예제(Slide 9)의 최적화**
우리가 살펴본 예제에서 $x5$와 $x6$는 '임시 레지스터'입니다. 규약에 따르면, 호출자가 이 값을 나중에 쓰겠다고 따로 저장해두지 않은 이상 피호출자는 이들을 스택에 저장할 의무가 없습니다. 즉, $x5, x6$에 대한 `sw`(Store) 두 번과 `lw`(Load) 두 번을 코드에서 과감히 삭제할 수 있습니다. 

**결론적으로**, 우리는 오직 반드시 보존해야 하는 레지스터($x20$과 같은 `Saved register`)만 스택에 저장함으로써, 메모리 접근 횟수를 줄이고 프로그램의 성능을 비약적으로 높일 수 있습니다.


## 1.3 중첩 및 비리프(Non-leaf) 프로시저 분석 (Slide 13~16)

프로시저 내부에서 또 다른 프로시저를 호출하는 경우를 `Nested procedure`(중첩 프로시저) 또는 `Non-leaf procedure`(비리프 프로시저)라고 합니다. 이 경우 복귀 주소와 데이터가 덮어씌워지는 문제가 발생하므로 정교한 스택 관리가 필수적입니다.

### Slide 13: Nested procedure

우리는 지금까지 다른 함수를 호출하지 않고 자기 할 일만 하고 끝나는 '리프 프로시저'($Leaf$ $procedure$)를 살펴봤습니다. 하지만 실제 프로그램에서는 함수 내부에서 또 다른 함수를 호출하는 경우가 훨씬 더 많습니다. 이를 `Non-leaf procedure`(비리프 프로시저) 또는 `Nested procedure`(중첩 프로시저)라고 부릅니다. 이 상황에서는 단순히 레지스터를 쓰는 것 이상의 세심한 관리가 필요합니다.

**1. 중첩 호출의 치명적인 문제점**
함수 A가 실행되다가 함수 B를 호출한다고 가정해 봅시다. 
*   함수 A가 처음 호출될 때, 메인 프로그램으로 돌아갈 복귀 주소는 $x1$ 레지스터에 저장됩니다.
*   그런데 함수 A 내부에서 `jal` 명령어로 함수 B를 호출하는 순간, $x1$ 레지스터의 값은 **함수 B가 끝난 뒤 함수 A로 돌아올 주소로 덮어씌워져 버립니다.**
*   결과적으로 함수 A는 자신의 작업을 마친 뒤 메인 프로그램으로 돌아가려 해도, 원래의 복귀 주소를 잃어버려 길을 잃게 됩니다.

**2. 해결책: 스택에 미리 보관하기**
이 문제를 해결하기 위해, 호출자($Caller$) 역할을 하는 함수는 다른 함수를 부르기 전에 다음 데이터들을 `stack`에 미리 저장해 두어야 합니다.
*   **자신의 복귀 주소 ($x1$)**: 나중에 메인 프로그램으로 무사히 돌아가기 위해 반드시 필요합니다.
*   **나중에 또 써야 할 인자와 임시 값들**: 함수 B를 실행하면서 $x10$ ~ $x17$이나 임시 레지스터들의 값이 바뀔 수 있기 때문에, 호출 후에도 이 값들이 필요하다면 미리 대피시켜야 합니다.

**3. 실행 흐름**
함수 호출이 끝나고 돌아온 직후, 스택에 저장해 두었던 값들을 다시 레지스터로 복구($Restore$)합니다. 그러면 함수 A는 마치 아무 일도 없었던 것처럼 자신의 남은 작업을 이어갈 수 있고, 최종적으로 원래의 복귀 주소를 찾아 메인 프로그램으로 돌아갈 수 있습니다.

### Slide 14: Nested procedure – Cont’d

중첩 프로시저 호출 시 발생하는 구체적인 충돌 상황을 예시를 통해 살펴보겠습니다. 메인 프로그램이 함수 A를 호출하고, 함수 A가 다시 함수 B를 호출하는 전형적인 상황입니다.

**1. 발생할 수 있는 충돌 시나리오**
*   **복귀 주소 충돌**: 메인 프로그램이 `jal x1, A`를 실행하면 $x1$에는 메인으로 돌아갈 주소가 담깁니다. 그런데 함수 A 내부에서 다시 `jal x1, B`를 실행하면, $x1$의 값은 함수 B에서 A로 돌아올 주소로 덮어씌워집니다. 메인으로 돌아갈 길을 잃어버리는 것입니다.
*   **인자 레지스터 충돌**: 메인 프로그램이 함수 A에 인자 `3`을 전달하기 위해 $x10$에 저장했다고 가정합시다. 그런데 함수 A가 함수 B를 부르기 위해 $x10$에 새로운 인자 `7`을 넣는 순간, 원래 A가 가지고 있던 데이터 `3`은 사라집니다.

**2. 해결책: 스택에 밀어넣기 (Pushing onto the stack)**
이러한 충돌을 방지하기 위해, 보존이 필요한 레지스터들을 `stack`에 저장해야 합니다. RISC-V의 관례에 따라 책임 소재를 나눕니다.
*   **호출자 (Caller)의 책임**: 함수 A는 자신이 함수 B를 호출한 이후에도 계속 사용해야 하는 인자 레지스터($x10$ ~ $x17$)나 임시 레지스터($x5$ ~ $x7$, $x28$ ~ $x31$)가 있다면, 호출 전에 이를 스택에 저장해야 합니다.
*   **피호출자 (Callee)의 책임**: 함수 A는 자신의 작업 시작 전에 복귀 주소 레지스터($x1$)와 자신이 사용할 예정인 저장 레지스터($x8$ ~ $x9$, $x18$ ~ $x27$)를 스택에 저장해야 합니다.

**3. 스택 관리**
레지스터를 스택에 저장할 때마다 `sp`(스택 포인터)를 적절히 조정하여 데이터가 겹치지 않게 관리합니다. 작업이 모두 끝나고 돌아갈 때는 반드시 저장했던 순서의 역순으로 값을 꺼내어($Pop$) 레지스터를 원상복구해야 합니다.

이 규칙을 철저히 지키면, 함수가 몇 단계로 중첩되어 호출되더라도 각 단계의 데이터와 복귀 주소를 안전하게 지킬 수 있습니다.

### Slide 15: Non-Leaf procedure example

앞서 배운 중첩 프로시저의 원리를 가장 명확하게 보여주는 사례는 자기 자신을 다시 호출하는 `Recursive function`(재귀 함수)입니다. 이번 장에서는 대표적인 재귀 함수인 팩토리얼($n!$) 계산을 통해, 비리프 프로시저가 어셈블리 수준에서 어떻게 설계되어야 하는지 그 기초를 다룹니다.

**1. 분석할 C 코드**
```c
int fact (int n)
{ 
 if (n < 1) return 1;
 else return (n * fact(n - 1));
}
```
*   **논리 구조**: 
    1.  **Base case (기본 조건)**: 입력값 `n`이 1보다 작으면 재귀를 멈추고 `1`을 반환합니다.
    2.  **Recursive step (재귀 단계)**: 그렇지 않으면 현재 값 `n`에 `fact(n-1)`의 결과값을 곱하여 반환합니다.

**2. 하드웨어 관점에서의 고민**
이 함수를 컴파일하기 위해 다음과 같은 가정을 세웁니다.
*   매개변수 `n`은 인자 레지스터인 `x10`에 들어있습니다.
*   함수 내부에서 `fact(n-1)`을 호출하기 위해 `jal` 명령어를 사용하게 됩니다.

**3. 스택 저장이 필요한 이유**
`fact` 함수가 자기 자신을 호출하는 순간, 두 가지 중요한 정보가 소실될 위기에 처합니다.
*   **복귀 주소 (`ra`, `x1`)**: `fact(n)`이 끝난 뒤 자기를 불렀던 곳으로 돌아가야 하는데, 내부에서 `fact(n-1)`을 호출하면서 `x1` 값이 덮어씌워집니다.
*   **현재 인자값 (`n`, `x10`)**: 재귀 호출이 끝나고 돌아와서 `n * 결과값` 연산을 해야 하는데, 재귀 호출을 위해 `x10`에 `n-1`을 넣는 순간 원래의 `n` 값이 사라집니다.

따라서 우리는 이 두 값을 반드시 `stack`에 보존해야 합니다. 다음 슬라이드에서 이 로직이 실제 어셈블리 코드로 어떻게 변환되는지 구체적으로 살펴보겠습니다.

### Slide 16: Non-leaf procedure example

앞선 **Slide 15**에서 살펴본 재귀 팩토리얼 함수의 C 코드를 실제 RISC-V 어셈블리어로 변환한 전체 코드입니다. 이 코드는 비리프 프로시저가 어떻게 자신의 상태를 보존하고 복구하는지 보여주는 가장 완벽한 예시입니다. 코드를 크게 세 부분으로 나누어 분석해 보겠습니다.

**1. 준비 단계: 프롤로그 (Prologue)**
*   `addi sp, sp, -8`: 레지스터 2개를 저장하기 위해 스택 공간 8바이트를 확보합니다.
*   `sw x1, 4(sp)`: 나중에 자기를 호출한 곳으로 돌아가기 위한 `return address`($ra$)를 스택에 저장합니다.
*   `sw x10, 0(sp)`: 현재의 인자값 $n$($a0$)을 스택에 저장합니다. 재귀 호출 후에 이 값이 다시 필요하기 때문입니다.

**2. 기본 케이스 처리 (Base Case: $n < 1$)**
*   `addi x5, x10, -1`: $x5 = n - 1$ 연산을 수행합니다.
*   `bge x5, x0, else`: 만약 $n-1 \ge 0$ (즉, $n \ge 1$)이라면 재귀 단계인 `else` 라벨로 점프합니다.
*   조건에 맞지 않을 때 ($n < 1$):
    *   `addi x10, x0, 1`: 결과값 레지스터 $x10$에 1을 담습니다 ($return\ 1$).
    *   `addi sp, sp, 8`: 스택을 정리하고 `jalr`로 즉시 반환합니다.

**3. 재귀 단계 처리 (Recursive Step: $else$)**
*   **재귀 호출**: `addi x10, x10, -1`로 인자를 $n-1$로 바꾼 뒤, `jal x1, fact`를 호출합니다. 이때 새로운 복귀 주소가 $x1$에 기록되지만, 우리는 원래 주소를 이미 스택에 치워두었으므로 안전합니다.
*   **복구 및 계산**:
    *   `addi x6, x10, 0`: 재귀 호출의 결과값($fact(n-1)$)을 잠시 $x6$에 옮겨둡니다.
    *   `lw x10, 0(sp)`, `lw x1, 4(sp)`: 스택에 비축해두었던 **원래의 $n$ 값**과 **원래의 복귀 주소**를 다시 읽어옵니다.
    *   `addi sp, sp, 8`: 사용한 스택 공간을 반환합니다.
    *   `mul x10, x10, x6`: 최종적으로 $n \times fact(n-1)$ 연산을 수행하여 결과값을 $x10$에 저장합니다.
*   **최종 반환**: `jalr x0, 0(x1)`을 통해 호출자에게 돌아갑니다.

**핵심 포인트**
이 코드에서 가장 중요한 부분은 `jal` 호출 전후로 스택을 통해 $x1$($ra$)과 $x10$($a0$)을 지켜냈다는 점입니다. 만약 이를 소홀히 했다면 무한 루프에 빠지거나 엉뚱한 값을 곱하게 되었을 것입니다. 이처럼 비리프 프로시저는 반드시 자신의 `context`(문맥)를 스택에 보존해야 합니다.

## 1.4 변수 유형(Local/Static) 및 레지스터 사용 관례 요약 (Slide 17~20)

프로시저 호출 시 데이터가 메모리의 어디에 저장되고 어떻게 관리되는지는 변수의 `Storage class`(저장 클래스)에 따라 달라집니다. 또한, 복잡한 메모리 참조를 돕는 프레임 포인터와 전체 레지스터의 표준 사용 규칙을 정리합니다.

### Slide 17: Automatic and static variables

우리가 프로그래밍을 할 때 사용하는 변수들은 데이터 타입(`int`, `char` 등)뿐만 아니라, 메모리에 얼마나 오랫동안 머무르는지를 결정하는 `Storage class`(저장 클래스)에 의해서도 해석이 달라집니다. 이번 장에서는 변수의 생명 주기와 이를 관리하기 위한 하드웨어적 기법을 살펴봅니다.

**1. 자동 변수 (Automatic variables)**
*   함수 내부에서 선언되는 일반적인 지역 변수들을 의미합니다.
*   함수가 호출될 때 생성되고, 함수가 종료되면 자동으로 파괴(`Discarded`)됩니다.
*   우리가 앞서 배운 `stack`(스택) 영역이 바로 이 자동 변수들을 저장하기 위한 공간입니다.

**2. 정적 변수 (Static variables)**
*   함수의 실행이 끝나고 제어권이 반환되어도 그 값이 소멸하지 않고 유지되는 변수입니다.
*   C 언어에서 `static` 키워드를 붙여 선언하거나, 어떤 함수에도 속하지 않는 외부(전역 변수)에 정의함으로써 만들 수 있습니다.
*   이들은 프로그램이 시작될 때 메모리의 특정 구역(`Static data segment`)에 자리 잡으며 프로그램이 끝날 때까지 존재합니다.

**3. 글로벌 포인터 (Global pointer, $x3$ 혹은 $gp$)**
*   정적 데이터나 전역 변수에 접근할 때마다 매번 복잡한 주소 계산을 수행하는 것은 비효율적입니다.
*   따라서 일부 RISC-V 컴파일러는 레지스터 **$x3$**를 `global pointer`($gp$)로 예약하여 사용합니다. 
*   이 레지스터가 정적 데이터가 모여 있는 영역의 기준 주소를 항상 가리키게 함으로써, 전역 변수에 훨씬 빠르고 간편하게 접근할 수 있도록 돕습니다.

**요약하자면**, 변수는 성격에 따라 스택에 잠시 머무는 '자동 변수'와 전용 구역에 계속 머무는 '정적 변수'로 나뉘며, 프로세서는 이를 효율적으로 관리하기 위해 $gp$와 같은 전용 레지스터를 활용합니다.

### Slide 18: Frame pointer

우리는 지금까지 레지스터가 부족할 때 데이터를 대피시키는 용도로 스택을 배웠습니다. 하지만 스택의 또 다른 중요한 용도는 레지스터에 담기에는 너무 큰 **지역 변수들을 저장**하는 것입니다. 예를 들어, 함수 안에서 선언된 큰 배열(Array)이나 복잡한 구조체(Structure)는 64비트 레지스터 하나에 들어갈 수 없으므로 메모리 공간인 스택에 자리를 잡아야 합니다.

**1. 프로시저 프레임 (Procedure frame)**
특정 프로시저가 실행되는 동안 스택 메모리에 할당되는 전용 공간을 `procedure frame`(프로시저 프레임) 또는 `stack frame`(스택 프레임)이라고 부릅니다. 이 프레임 안에는 다음과 같은 정보들이 차곡차곡 쌓입니다.
*   함수가 전달받은 인자 레지스터들 (필요한 경우)
*   돌아갈 복귀 주소 ($ra$)
*   함수 내부에서 사용하기 위해 보존해둔 저장 레지스터들 ($s0$ ~ $s11$)
*   레지스터에 담지 못한 지역 배열이나 구조체 데이터

**2. 스택의 변화 과정 (도식 설명)**
슬라이드 하단의 그림을 통해 프레임이 생성되고 사라지는 과정을 살펴봅시다.
*   **(a) 호출 전**: $SP$(스택 포인터)와 $FP$(프레임 포인터)가 이전 함수의 경계 지점을 가리키고 있습니다.
*   **(b) 호출 중**: 새로운 함수가 실행되면서 $SP$를 아래로 내려 공간을 확보합니다. 이 확보된 영역이 바로 현재 함수의 `stack frame`입니다. 그림을 보면 복귀 주소, 저장된 레지스터, 지역 배열 등이 이 구역 안에 옹기종기 모여 있는 것을 볼 수 있습니다.
*   **(c) 호출 후**: 함수의 작업이 끝나면 $SP$를 다시 위로 올려 프레임을 없앱니다. 이제 이 공간은 다른 함수가 사용할 수 있는 빈 공간이 됩니다.

**정리하자면**, 프로시저 프레임은 각 함수가 자신만의 독립적인 업무 공간을 메모리에 확보하는 방식입니다. 여기서 새롭게 등장한 $FP$라는 개념이 왜 필요한지에 대해서는 바로 다음 장에서 더 자세히 다루겠습니다.

### Slide 19: Frame pointer – Cont’d

앞선 **Slide 18**에서 스택 프레임의 개념을 배웠습니다. 이번 장에서는 왜 우리가 $sp$ 외에 `frame pointer`($fp$)라는 별도의 레지스터를 추가로 사용하는지 그 실질적인 이유와 8개가 넘는 인자를 처리하는 법을 알아봅니다.

**1. $sp$의 한계: 변하는 기준점**
*   `stack pointer`($sp$)는 프로시저가 실행되는 도중에도 값이 변할 수 있습니다. 예를 들어, 함수 중간에 임시로 데이터를 스택에 넣었다 뺐다 하면 $sp$의 위치가 계속 오르내리게 됩니다.
*   이렇게 되면 메모리에 있는 지역 변수를 참조할 때, 명령어에 적어야 하는 오프셋($Offset$) 값이 코드의 위치에 따라 매번 달라집니다. 이는 컴파일러가 코드를 생성하기 복잡하게 만들고, 사람이 어셈블리 코드를 이해하기 어렵게 합니다.

**2. $fp$의 해결책: 변하지 않는 기준점**
*   일부 RISC-V 컴파일러는 레지스터 **$x8$**($s0$ 또는 $fp$)을 `frame pointer`로 예약하여 사용합니다. 
*   이 레지스터는 프로시저가 시작될 때의 스택 위치, 즉 **프레임의 첫 번째 워드**를 가리킨 채 고정됩니다.
*   함수 실행 도중 $sp$가 아무리 움직여도 $fp$는 제자리를 지키기 때문에, 지역 변수들에 접근할 때 항상 일정한 오프셋을 사용할 수 있는 안정적인 `stable base register` 역할을 수행합니다.

**3. 인자가 8개를 넘을 때의 처리법**
우리는 RISC-V 관례상 처음 8개의 인자는 레지스터 $x10$ ~ $x17$에 넣는다고 배웠습니다. 그렇다면 만약 인자가 9개, 10개라면 어떻게 해야 할까요?
*   규약에 따르면, 처음 8개는 레지스터를 통해 전달하고 **나머지 인자들은 메모리(스택)에 저장**하여 전달합니다.
*   이때 스택에 저장된 추가 인자들은 **$fp$ 바로 위쪽**에 위치하게 됩니다. 따라서 함수 내부에서는 $fp$를 기준으로 오프셋을 계산하여 이 추가 인자들을 손쉽게 읽어올 수 있습니다.

**요약하자면**, 프레임 포인터는 함수 내부에서 메모리 데이터를 찾기 위한 **"흔들리지 않는 기준점"**입니다. 이를 통해 복잡한 지역 변수와 많은 수의 인자를 훨씬 체계적으로 관리할 수 있습니다.

### Slide 20: RISC-V register summary

이번 장은 지금까지 학습한 모든 레지스터의 역할과 약속을 총정리하는 매우 중요한 지점입니다. RISC-V에는 총 32개의 일반 목적 레지스터가 있지만, 프로그래머와 컴파일러가 이를 효율적이고 안전하게 사용하기 위해 `ABI`(Application Binary Interface)라는 표준 규약을 정해두었습니다. 이 규약은 "누가 이 레지스터의 값을 책임지고 지킬 것인가"를 정의합니다.

**1. RISC-V 레지스터 상세 요약표**

| 레지스터 (Register) | ABI 명칭 (Name) | 설명 (Description) | 보존 책임 (Saver) |
| :--- | :--- | :--- | :--- |
| $x0$ | `zero` | 하드웨어적으로 고정된 0 값 | -- |
| $x1$ | `ra` | 리턴 주소 (Return address) | **Caller** |
| $x2$ | `sp` | 스택 포인터 (Stack pointer) | **Callee** |
| $x3$ | `gp` | 글로벌 포인터 (Global pointer) | -- |
| $x4$ | `tp` | 스레드 포인터 (Thread pointer) | -- |
| $x5 - x7$ | `t0 - t2` | 임시 레지스터 (Temporaries) | **Caller** |
| $x8$ | `s0 / fp` | 저장 레지스터 / 프레임 포인터 | **Callee** |
| $x9$ | `s1` | 저장 레지스터 (Saved register) | **Callee** |
| $x10 - x11$ | `a0 - a1` | 함수 인자 및 결과 반환 값 | **Caller** |
| $x12 - x17$ | `a2 - a7` | 함수 인자 (Arguments) | **Caller** |
| $x18 - x27$ | `s2 - s11` | 저장 레지스터 (Saved registers) | **Callee** |
| $x28 - x31$ | `t3 - t6` | 임시 레지스터 (Temporaries) | **Caller** |

**2. 보존 책임(Saver)의 구체적 의미**
이 표에서 가장 핵심적인 개념은 `Saver` 열입니다. 이는 함수 호출이 일어날 때 기존 데이터를 지켜야 할 주체가 누구인지를 나타냅니다.

*   **호출자 보존 (Caller-saved)**: `ra`, `t0-t6`, `a0-a7` 등이 해당합니다.
    *   함수를 부르는 쪽(Caller)에서 이 레지스터의 값이 나중에 또 필요하다면, 함수를 부르기 전에 **자기가 직접 스택에 저장**해야 합니다. 
    *   반대로 함수를 호출당하는 쪽(Callee)은 이 레지스터들을 마음대로 쓰고 값을 바꿔도 미안해할 필요가 없습니다.
*   **피호출자 보존 (Callee-saved)**: `sp`, `s0-s11` 등이 해당합니다.
    *   이 레지스터들은 매우 소중한 데이터가 담긴 것으로 간주합니다.
    *   따라서 호출당한 함수(Callee)가 이 레지스터들을 사용하고 싶다면, 반드시 **사용 전에 스택에 값을 대피시켰다가 종료 전에 복구**해 놓아야 합니다. 호출한 쪽에서는 이 레지스터들의 값이 함수 호출 전후로 변하지 않을 것이라고 믿고 작업합니다.

**3. 왜 이렇게 나누나요?**
모든 레지스터를 매번 스택에 저장하는 것은 엄청난 성능 낭비입니다. 따라서 "자주 바뀌어도 되는 값(`t` 레지스터)"과 "함수가 끝나도 유지되어야 하는 값(`s` 레지스터)"을 구분하여, 꼭 필요한 상황에서만 메모리에 접근하도록 최적화하기 위해 이러한 규약을 사용합니다.

# 대주제 2. 메모리 레이아웃 및 정렬 알고리즘 사례 (Slide 21~33)

## 2.1 프로그램 메모리 구조: Text, Data, Heap, Stack (Slide 21~24)

### Slide 21: Memory Layout

우리가 작성한 C 프로그램이 실행 파일이 되어 메모리에 올라가면, 운영체제는 효율적인 관리를 위해 메모리를 용도별로 여러 구역(Segment)으로 나누어 배치합니다. 이번 장에서는 프로그램이 사용하는 전체적인 메모리 지도인 `Memory Layout`을 살펴보겠습니다.

**1. 메모리 영역의 주요 구성 요소**

| 영역 (Segment) | 설명 (Description) | 관련 키워드 |
| :--- | :--- | :--- |
| `Stack` | 함수 내의 지역 변수(`automatic variables`)를 저장하는 공간 | 함수 호출, 지역 변수 |
| `Dynamic data` | 프로그램 실행 중에 크기가 결정되는 동적 데이터를 위한 공간 | `malloc` (C), `new` (Java) |
| `Static data` | 프로그램 시작부터 끝까지 유지되는 전역/정적 변수를 위한 공간 | `static`, 전역 변수 |
| `Text` | 작성한 프로그램의 기계어 명령어(`instructions`)가 저장되는 공간 | 프로그램 소스 코드 |
| `Reserved` | 운영체제가 시스템 관리를 위해 예약해 둔 공간 (보통 주소 0 근처) | 시스템 예약 |

**2. 메모리 주소와 성장 방향**
슬라이드 중앙의 도식은 메모리 주소가 낮은 곳($0$)부터 높은 곳($High\ address$)까지 어떻게 나뉘는지 보여줍니다.
*   **하단 (Low Address)**: 가장 아래에는 `Reserved` 영역이 있고, 그 위로 실제 우리가 작성한 코드가 담긴 `Text` 영역이 위치합니다. $PC$(프로그램 카운터)는 보통 이 `Text` 영역의 시작점인 `0000 0000 0040 0000` 부근을 가리키며 실행을 시작합니다.
*   **중간 (Data & Heap)**: 코드 위로는 정적 변수들이 모인 `Static data`가 있고, 그 위에는 실행 중 메모리를 할당받는 `Dynamic data` 영역이 위치합니다. 이 영역은 위쪽(높은 주소) 방향으로 자라납니다.
*   **상단 (High Address)**: 메모리의 가장 높은 곳에는 `Stack` 영역이 있습니다. $SP$(스택 포인터)는 약 `0000 003f ffff fff0` 부근에서 시작하며, 데이터가 쌓일수록 **아래쪽(낮은 주소) 방향으로 자라납니다.**

**3. 왜 서로 반대 방향으로 자라나요?**
`Stack`은 위에서 아래로, `Dynamic data`(Heap)는 아래에서 위로 자라게 설계함으로써, 그 사이의 빈 공간을 최대한 유연하게 나누어 쓸 수 있도록 한 것입니다. 한쪽이 많이 필요하면 그만큼 빈 공간을 더 가져다 쓸 수 있는 구조입니다.

**요약하자면**, 메모리 레이아웃은 프로그램의 '코드', '전역 변수', '동적 변수', '지역 변수'가 각각 자기만의 집을 짓고 사는 지도와 같습니다. 각 영역이 어디에 위치하고 어느 방향으로 커지는지를 이해하는 것은 효율적인 프로그래밍과 디버깅의 기초가 됩니다.


## 2.1 프로그램 메모리 구조: Text, Data, Heap, Stack (Slide 21~24)

### Slide 22: Memory Layout – Cont’d

앞선 **Slide 21**에서 메모리의 전체적인 지도를 그렸다면, 이번 장에서는 각 영역이 구체적으로 어떤 데이터를 담고 어떻게 관리되는지 상세히 분석해 보겠습니다. 각 세그먼트의 특성을 이해하면 프로그램이 실행될 때 발생하는 메모리 오류를 방지하는 데 큰 도움이 됩니다.

**1. 메모리 세그먼트별 특징 요약**

| 세그먼트 (Segment) | 역할 및 포함 데이터 (Role & Data) | 특징 (Characteristics) |
| :--- | :--- | :--- |
| **`Text`** | 컴파일된 프로그램의 이진 기계어 코드 | 읽기 전용(Read-only), 크기 고정 |
| **`Static Data`** | 상수가 포함된 전역 및 정적 변수 영역 | 초기값 유무에 따라 두 구역으로 분리 |
| **`Heap`** | 실행 중 요청에 따라 할당되는 동적 메모리 | 높은 주소 방향으로 성장 ($\uparrow$) |
| **`Stack`** | 함수 호출 시의 지역 변수 및 레지스터 값 | 낮은 주소 방향으로 성장 ($\downarrow$) |

**2. 세부 영역 설명**

*   **`Text segment`**: 우리가 작성한 소스 코드가 컴파일되어 하드웨어가 읽을 수 있는 기계어 상태로 저장되는 곳입니다. 실행 중에 코드가 변하면 안 되므로 보통 쓰기가 금지되어 있습니다.
*   **`(static) data segment`**: 프로그램 전체에서 공유되는 변수들이 담깁니다.
    *   **Initialized data**: 초기값이 있는 정적 변수용 공간입니다.
    *   **Uninitialized data**: 초기값이 없는 변수들을 위한 공간(BSS 영역)입니다.
*   **`Heap segment`**: C 언어의 `malloc`, `realloc` 혹은 Java의 `new` 키워드를 통해 만들어지는 데이터가 위치합니다. 프로그램 실행 중에 크기가 유동적으로 변하며, 운영체제에 메모리 확장을 요청할 때 `brk`나 `sbrk` 같은 시스템 콜을 사용하여 주소 경계선을 조절합니다.
*   **`Stack segment`**: 이미 학습했듯이, 함수가 호출될 때마다 생기는 프레임들이 쌓이는 곳입니다. 지역 변수가 여기에 속하며, 데이터가 들어찰수록 주소 값이 작아지는 방향으로 확장됩니다.

**요약하자면**, 프로그램은 코드(`Text`)와 약속된 변수(`Data`)를 먼저 배치한 뒤, 실행 중에 필요한 데이터는 아래에서 위로(`Heap`), 함수 호출에 필요한 데이터는 위에서 아래로(`Stack`) 채워 나가며 메모리를 효율적으로 사용합니다.

### Slide 23: Memory Layout – Cont’d

이번 장은 앞서 배운 메모리 구조의 이론이 실제 C 언어 코드에서 어떻게 구체화되는지 보여주는 매우 중요한 시각화 자료입니다. 코드의 각 줄이 메모리의 어느 구역에 저장되는지 일대일로 매칭하며 살펴보겠습니다.

**1. 코드와 메모리 영역의 매핑 (Mapping)**

| C 코드 예시 | 저장되는 메모리 영역 (Segment) | 특징 |
| :--- | :--- | :--- |
| `int argc, char *argv[]` | **최상단 (High memory)** | 프로그램 실행 시 전달되는 인자들 |
| `int *values;`, `int i;` | **`stack`** | `main` 함수 내부에서 선언된 지역 변수 |
| `malloc(sizeof(int)*5)` | **`heap`** | 실행 중에 할당받은 동적 데이터 공간 |
| `int x;` | **`uninitialized data`** | 초기값이 없는 전역/정적 변수 |
| `int y = 15;` | **`initialized data`** | 초기값이 있는 전역/정적 변수 |
| `return 0;` 및 전체 로직 | **`text`** | 컴파일된 실제 기계어 명령어들 |

**2. 주요 포인트 분석**

*   **인자와 스택**: 함수의 매개변수인 `argc`, `argv`는 메모리의 가장 높은 곳에 위치하며, 그 아래로 함수 내의 지역 변수들이 `stack` 프레임을 형성하며 쌓입니다. 그림의 화살표처럼 아래 방향($\downarrow$)으로 자라납니다.
*   **동적 할당의 목적지**: `malloc`으로 생성된 데이터는 `heap` 영역에 자리 잡습니다. 이 영역은 화살표처럼 위 방향($\uparrow$)으로 확장되며 스택과 서로 마주 보는 구조를 가집니다.
*   **데이터의 세분화**: 전역 변수 중에서도 값이 정해진 `y`는 `initialized data`에, 선언만 된 `x`는 `uninitialized data`에 나뉘어 들어가는 점을 눈여겨보아야 합니다.
*   **코드의 위치**: 우리가 짠 모든 논리 구조는 `text` 영역에 기계어로 변환되어 가장 낮은 주소 쪽에 안전하게 보관됩니다.

**요약하자면**, 우리가 무심코 작성하는 코드 한 줄 한 줄은 하드웨어 입장에서 각각 정해진 '주소'와 '구역'을 찾아가게 됩니다. 이 그림을 머릿속에 넣어두면, 나중에 포인터 오류나 메모리 부족 현상이 발생했을 때 어떤 영역에서 문제가 생겼는지 훨씬 쉽게 추론할 수 있습니다.

프로세서와 메모리 사이의 데이터 흐름을 보여줍니다.
*   **명령어 인출 ($Fetch$ $instruction$)**: 프로세서는 `Text` 영역에서 명령어를 가져옵니다.
*   **데이터 로드/스토어 ($Load/Store$)**: 프로세서의 `Control`과 `Datapath` 유닛은 `Stack`과 `Heap` 영역에 데이터를 쓰거나 읽어옵니다.
*   **특징**: 레지스터는 매우 빠르지만 공간이 한정적이며, 메모리는 레지스터보다 느리지만 훨씬 큰 공간을 제공합니다.

## 2.2 C 정렬(Insertion Sort) 예제와 어셈블리 변환 (Slide 25~33)

### Slide 25: A C sort example (ch. 2.13, COD book)

이제부터는 우리가 지금까지 개별적으로 학습한 모든 지식—프로시저 호출 규약, 레지스터 보존 의무, 메모리 접근, 그리고 조건문 처리—을 하나로 합쳐서 복합적인 사례를 분석해 보겠습니다. 이번 섹션의 주제는 `A C sort example`입니다.

우리가 중점적으로 분석할 알고리즘은 `Insertion Sort`(삽입 정렬)입니다. 다음 슬라이드부터 이 알고리즘의 C 소스 코드를 확인하고, 이를 단계별로 쪼개어 RISC-V 어셈블리 명령어로 재구성하는 과정을 상세히 추적해 보겠습니다.


### Slide 26: Insertion sort in C

이번 슬라이드에서는 본격적인 어셈블리 변환에 앞서, 대상이 되는 `Insertion sort`(삽입 정렬)의 C 언어 소스 코드를 분석합니다. 삽입 정렬은 이미 정렬된 부분에 새로운 원소를 하나씩 적절한 위치에 '삽입'해 나가는 알고리즘입니다.

**1. 코드 구조 분석**

*   **함수 정의**: `sort(int v[], int n)`는 정수형 배열의 시작 주소인 `v[]`와 배열의 크기인 `n`을 인자로 받습니다.
*   **외부 루프 (Outer loop)**: 인덱스 `i`가 1부터 `n-1`까지 하나씩 증가합니다. 현재 정렬의 대상이 되는 원소인 `v[i]`를 `temp`라는 변수에 임시로 보관합니다.
*   **내부 루프 (Inner loop)**: 인덱스 `j`는 `i-1`부터 시작하여 0까지 역순으로 진행됩니다. 
    *   **조건**: 현재 위치의 값 `v[j]`가 `temp`보다 크다면, 이 값을 오른쪽으로 한 칸 밀어냅니다 (`v[j+1] = v[j]`).
    *   이 과정을 통해 `temp`가 들어갈 적절한 빈자리를 만듭니다.
*   **삽입 (Insertion)**: 내부 루프가 종료되면(즉, `temp`보다 작거나 같은 값을 찾으면), 그 바로 오른쪽 칸에 보관해두었던 `temp`를 저장합니다 (`v[j+1] = temp`).

**2. 하드웨어 관점에서의 주요 과제**

이 코드를 어셈블리로 바꿀 때 우리는 다음 사항들에 주목해야 합니다.
1.  **배열 접근**: `v[i]`나 `v[j]`와 같은 배열 원소에 접근하기 위해 베이스 주소에 오프셋(인덱스 $\times$ 4바이트)을 더하는 연산이 필요합니다.
2.  **이중 루프 제어**: 외부 루프(`i`)와 내부 루프(`j`)를 관리하기 위한 인덱스 레지스터와 조건 분기 명령어가 사용됩니다.
3.  **변수 매핑**: `v`, `n`, `i`, `j`, `temp` 등의 변수들을 어떤 레지스터에 할당하고, 어떤 레지스터를 스택에 보존할지 결정해야 합니다.

**요약하자면**, 삽입 정렬은 중첩된 루프와 조건문, 그리고 빈번한 메모리 접근이 일어나는 알고리즘입니다. 다음 장부터는 이 로직을 구현하기 위해 RISC-V 레지스터를 어떻게 전략적으로 배치하는지 단계별로 살펴보겠습니다.

### Slide 27: Insertion sort in C – Cont’d

이제 앞서 살펴본 C 언어 정렬 함수를 실제 RISC-V 어셈블리 코드로 변환하는 첫 번째 단계인 **Step 1: Prologue(프롤로그)** 과정을 분석해 보겠습니다. 프롤로그는 함수가 본격적인 작업을 시작하기 전에, 남의 물건(호출자의 레지스터)을 빌려 쓰기 위해 준비를 하는 과정입니다.

**1. 어셈블리 코드 분석**

| 명령어 (Instruction) | 설명 (Description) |
| :--- | :--- |
| `Sort:` | 함수의 시작을 알리는 라벨입니다. |
| `addi sp, sp, -12` | 레지스터 3개를 저장하기 위해 `sp`를 12바이트만큼 아래로 내려 공간을 확보합니다. |
| `sw ra, 8(sp)` | 함수가 끝난 뒤 돌아갈 복귀 주소(`ra`)를 스택에 저장합니다. |
| `sw s1, 4(sp)` | 나중에 사용할 저장 레지스터 `s1`의 기존 값을 스택에 보존합니다. |
| `sw s2, 0(sp)` | 나중에 사용할 저장 레지스터 `s2`의 기존 값을 스택에 보존합니다. |

**2. 왜 이 레지스터들을 저장하나요?**

이 예제에서는 레지스터 보존 규약인 `ABI` 규칙을 철저히 따르고 있습니다.
*   **`ra` ($x1$)**: `sort` 함수 내부에서 또 다른 함수를 호출하지 않더라도(현재는 리프 프로시저처럼 보이지만), 함수 호출의 기본 습관으로서 복귀 주소를 지킵니다.
*   **`s1, s2` ($x9, x18-x27$)**: 이들은 `Callee-saved` 레지스터입니다. 즉, 이 함수(피호출자)가 이 레지스터들을 작업 공간으로 쓰고 싶다면, 호출자가 원래 담아두었던 값을 망가뜨리지 않도록 반드시 스택에 먼저 치워두어야 할 의무가 있습니다.

**3. 레지스터 보존 의무 요약**

| 레지스터 종류 | 보존 책임 (Saver) | 특징 |
| :--- | :--- | :--- |
| `t0 - t6` | **Caller** (호출자) | 함수를 부르는 쪽이 필요하면 알아서 지켜야 함. |
| `s1 - s11` | **Callee** (피호출자) | **함수를 호출당한 쪽이 반드시 원래대로 돌려놔야 함.** |

**요약하자면**, 정렬 함수는 본격적인 루프를 돌기 전에 스택에 자리를 만들고(`addi`), 나중에 돌려줘야 할 중요한 레지스터 값들을 안전하게 대피(`sw`)시키는 것으로 시작합니다.

### Slide 28: Insertion sort in C – Cont’d

**Slide 27**에서 중요한 레지스터들을 스택에 안전하게 보존하는 프롤로그 과정을 마쳤습니다. 이제 두 번째 단계인 **Step 2: Move parameter(매개변수 이동)** 과정을 살펴보겠습니다. 이 단계에서는 호출자로부터 전달받은 인자값들을 본격적인 연산을 위해 사용하기 편한 장소로 옮기는 작업을 수행합니다.

**1. 어셈블리 코드 분석**

| 명령어 (Instruction) | 설명 (Description) |
| :--- | :--- |
| `addi t0, a0, 0` | 인자 레지스터 `a0`에 담긴 배열 `v[]`의 주소값을 `t0` 레지스터로 복사합니다. |
| `addi t1, a1, 0` | 인자 레지스터 `a1`에 담긴 배열 크기 `n`의 값을 `t1` 레지스터로 복사합니다. |

**2. 왜 `addi` 명령어로 복사를 하나요?**

RISC-V 명령어 세트에는 레지스터 간의 값을 직접 복사하는 전용 `copy` 명령어가 따로 없습니다. 대신 더하기 연산인 `addi`(Add Immediate)를 활용하여 다음과 같은 트릭을 사용합니다.
*   $t0 = a0 + 0$ 이라는 연산을 수행하면, 결과적으로 $a0$의 값이 그대로 $t0$에 저장됩니다. 이는 하드웨어를 단순하게 유지하면서도 복사 기능을 완벽히 수행하는 효율적인 방법입니다.

**3. 인자를 이동시키는 이유**

함수가 전달받은 인자 레지스터(`a0`, `a1`)를 직접 사용하여 연산할 수도 있지만, 별도의 `temporary register`(`t0`, `t1`)로 옮겨서 사용하는 데에는 몇 가지 이유가 있습니다.
*   **원본 보존**: `a0`~`a7` 레지스터는 다른 함수를 호출할 때 다시 인자를 담는 용도로 사용될 수 있습니다. 따라서 중요한 기준값인 배열 주소와 크기를 `t` 레지스터에 복사해두면 코드를 관리하기 훨씬 수월해집니다.
*   **가독성**: 작업용 레지스터를 명확히 구분함으로써 이후 진행될 복잡한 루프 연산에서 혼동을 줄일 수 있습니다.

**요약하자면**, 이번 단계는 전달받은 재료(인자)를 요리하기 편한 그릇(`t0`, `t1`)에 옮겨 담는 과정입니다. 이제 모든 준비가 끝났으므로, 다음 장부터는 본격적으로 정렬 알고리즘의 핵심인 외부 루프($i$) 로직을 구현해 보겠습니다.

### Slide 29: Insertion sort in C – Cont’d

프롤로그와 인자 설정을 모두 마쳤으므로, 이제 정렬 알고리즘의 핵심인 `Outer loop`(외부 루프)를 구현하는 **Step 3: Outer loop 1** 과정을 살펴보겠습니다. C 코드의 `for (int i = 1; i < n; ++i)` 부분을 하드웨어 명령어로 번역하는 과정입니다.

**1. 어셈블리 코드 분석**

| 명령어 (Instruction) | 설명 (Description) |
| :--- | :--- |
| `addi t2, x0, 1` | 외부 루프 인덱스 $i$를 1로 초기화하여 $t2$ 레지스터에 저장합니다. |
| `Loop1:` | 외부 루프의 시작 지점을 나타내는 라벨입니다. |
| `bge t2, t1, Exit` | 만약 $i \ge n$ 이라면, 정렬이 완료된 것이므로 `Exit` 라벨로 점프하여 루프를 탈출합니다. |
| `slli t4, t2, 2` | 인덱스 $i$($t2$)에 $2^2$를 곱하는 연산($i \times 4$)을 수행하여 `Offset`을 계산합니다. |
| `add s1, t0, t4` | 배열의 시작 주소($t0$)에 오프셋($t4$)을 더해 $v[i]$의 실제 메모리 주소를 계산합니다. |
| `lw t4, 0(s1)` | 계산된 주소($s1$)로부터 실제 데이터 값을 읽어와 $t4$에 저장합니다. 이 $t4$가 C 코드의 `temp` 변수 역할을 합니다. |

**2. 주요 개념 설명**

*   **인덱스 초기화**: 삽입 정렬은 두 번째 원소(인덱스 1)부터 시작하므로 $t2$에 `1`을 넣습니다. 하드웨어적으로 항상 0인 $x0$ 레지스터를 활용하여 값을 생성합니다.
*   **조건 분기 (`bge`)**: `Branch if Greater or Equal`의 약자로, 루프의 종료 조건을 검사합니다. $i$가 $n$과 같아지는 순간 루프가 끝납니다.
*   **주소 계산의 원리 (`slli`)**: 컴퓨터 메모리는 바이트 단위로 주소가 매겨집니다. `int`형 데이터는 한 칸당 **4바이트**를 차지하므로, 배열의 $i$번째 칸에 접근하려면 인덱스에 반드시 4를 곱해줘야 합니다. 왼쪽으로 비트를 2칸 미는 `slli`(Shift Left Logical Immediate) 연산은 곱하기 4와 효율면에서 동일하므로 이를 사용합니다.
*   **베이스 주소와 오프셋**: 배열의 시작점인 `Base address`($t0$)와 계산된 거리인 `Offset`($t4$)을 더해 최종적인 데이터의 위치를 찾아내는 이 방식은 하드웨어 주소 지정의 가장 기본적인 패턴입니다.

**요약하자면**, 이번 단계에서는 루프를 시작하기 위한 인덱스를 설정하고, 현재 정렬할 대상인 `v[i]`의 값을 메모리에서 꺼내 `temp`($t4$)에 보관하는 작업을 마쳤습니다. 이제 이 `temp` 값을 적절한 위치에 끼워 넣기 위한 내부 루프 로직이 이어집니다.

### Slide 30: Insertion sort in C – Cont’d

외부 루프에서 정렬할 대상인 `temp` 값을 확보했으므로, 이제 그 값이 들어갈 적절한 위치를 찾는 `Inner loop`(내부 루프) 과정을 살펴보겠습니다. C 코드의 `for (int j = i - 1; j >= 0 && v[j] >= temp; --j)` 부분을 하드웨어 명령어로 구현하는 **Step 4: Inner loop** 단계입니다.

**1. 어셈블리 코드 분석**

| 명령어 (Instruction) | 설명 (Description) |
| :--- | :--- |
| `addi t3, t2, -1` | 내부 루프 인덱스 $j$를 $i-1$로 초기화하여 $t3$ 레지스터에 저장합니다. |
| **`Loop2:`** | 내부 루프의 시작 지점입니다. |
| `blt t3, x0, Loop3` | **첫 번째 조건 검사**: 만약 $j < 0$ 이라면 루프를 종료하고 `Loop3`로 이동합니다. |
| `slli t5, t3, 2` | 인덱스 $j$($t3$)에 4를 곱하여 바이트 오프셋을 계산합니다. |
| `add s2, t0, t5` | 배열 시작 주소($t0$)에 오프셋($t5$)을 더해 $v[j]$의 주소를 계산합니다. |
| `lw t5, 0(s2)` | 메모리에서 $v[j]$의 실제 값을 읽어와 $t5$에 저장합니다. |
| `blt t5, t4, Loop3` | **두 번째 조건 검사**: 만약 $v[j] < temp$($t4$) 라면 루프를 종료하고 `Loop3`로 이동합니다. |
| `sw t5, 4(s2)` | $v[j]$의 값을 오른쪽 칸($v[j+1]$)으로 밀어냅니다. $s2+4$가 바로 다음 칸의 주소입니다. |
| `addi t3, t3, -1` | 인덱스 $j$를 1 감소시킵니다 (`j--`). |
| `jal x0, Loop2` | 다시 `Loop2`의 처음으로 돌아가 조건을 검사합니다. |

**2. 주요 로직 분석**

*   **복합 조건 처리**: C 코드의 `&&` 조건은 어셈블리에서 두 번의 `blt`(Branch if Less Than) 명령어로 나누어 처리됩니다. 둘 중 하나라도 만족하지 않으면 즉시 루프를 탈출하여 효율성을 높입니다.
*   **데이터 이동 (Shifting)**: `sw t5, 4(s2)` 명령어가 핵심입니다. 현재 $s2$가 $v[j]$의 주소를 가리키고 있으므로, 여기에 오프셋 `4`를 더한 `4(s2)`는 자동으로 $v[j+1]$의 위치가 됩니다. 별도의 주소 계산 없이 `Store` 명령어의 오프셋 기능을 활용한 영리한 기법입니다.
*   **무한 루프 방지**: 루프의 끝에서 `j`를 감소시킨 뒤 `jal`을 통해 다시 위로 올라가 조건을 검사함으로써 반복 구조를 완성합니다.

**요약하자면**, 내부 루프는 $v[i]$보다 큰 값들을 오른쪽으로 한 칸씩 밀어내며 `temp`가 들어갈 빈자리를 만드는 과정입니다. 이제 적절한 삽입 위치를 찾았거나 루프가 끝났을 때 수행할 '값의 삽입' 과정이 이어집니다.

### Slide 31: Insertion sort in C – Cont’d

내부 루프를 통해 자신보다 큰 값들을 모두 오른쪽으로 밀어냈다면, 이제 비어있는 적절한 위치에 보관해두었던 값을 끼워 넣을 차례입니다. C 코드의 `v[j+1] = temp;` 부분과 외부 루프의 인덱스 증가(`++i`)를 처리하는 **Step 5: Outer loop 2** 단계를 분석하겠습니다.

**1. 어셈블리 코드 분석**

| 명령어 (Instruction) | 설명 (Description) |
| :--- | :--- |
| **`Loop3:`** | 내부 루프($j$)가 조건을 만족하지 못해 탈출했을 때 도달하는 지점입니다. |
| `slli t5, t3, 2` | 최종적인 인덱스 $j$($t3$)에 4를 곱해 오프셋을 계산합니다. |
| `add s2, t0, t5` | 배열 시작 주소에 오프셋을 더해 $v[j]$의 주소를 계산합니다. |
| `sw t4, 4(s2)` | **삽입(Insertion)**: 보관해두었던 `temp`($t4$)를 $v[j+1]$ 위치($s2+4$)에 저장합니다. |
| `addi t2, t2, 1` | 외부 루프 인덱스 $i$를 1 증가시킵니다 (`i++`). |
| `jal x0, Loop1` | 다음 원소를 정렬하기 위해 다시 외부 루프의 시작점인 `Loop1`으로 점프합니다. |

**2. 주요 로직 분석**

*   **삽입 위치의 결정**: 내부 루프가 종료된 시점의 $j$는 `temp`보다 작거나 같은 값을 가진 위치입니다. 따라서 우리가 값을 넣어야 할 곳은 그 바로 오른쪽인 $j+1$입니다. 어셈블리에서는 $v[j]$의 주소인 $s2$에 오프셋 `4`를 더한 `4(s2)` 주소를 사용해 이 로직을 간단히 구현합니다.
*   **외부 루프의 순환**: 한 원소에 대한 정렬이 끝났으므로 인덱스 $i$를 키우고 다시 위로 올라갑니다. 만약 $i$가 배열의 크기인 $n$에 도달했다면, **Slide 29**에서 보았던 `bge t2, t1, Exit` 명령어에 의해 전체 루프가 종료될 것입니다.
*   **레지스터의 재사용**: $t4$(`temp`)와 $t5$(계산용) 레지스터가 함수 전체에서 일관된 용도로 사용되고 있음을 확인할 수 있습니다.

**요약하자면**, 이번 단계는 찾은 자리에 값을 넣고 다음 칸으로 이동하는 '마무리 작업'입니다. 모든 루프가 종료되어 `Exit` 라벨로 이동하게 되면, 이제 처음에 빌렸던 레지스터들을 복구하고 함수를 완전히 종료하는 단계만 남게 됩니다.

### Slide 32: Insertion sort in C – Cont’d

모든 정렬 루프가 종료되면 프로그램은 `Exit` 라벨로 이동합니다. 이제 함수를 완전히 종료하기 전에, 처음에 수행했던 준비 작업(프롤로그)과 정반대로 뒷정리를 하는 과정인 `Epilogue`(에필로그)를 수행해야 합니다.

**1. 어셈블리 코드 분석**

| 명령어 (Instruction) | 설명 (Description) |
| :--- | :--- |
| **`Exit:`** | 루프를 모두 마치고 함수를 종료하기 위한 시작 지점입니다. |
| `lw s2, 0(sp)` | 스택에 저장해두었던 `s2`의 원래 값을 읽어와 복구합니다. |
| `lw s1, 4(sp)` | 스택에 저장해두었던 `s1`의 원래 값을 읽어와 복구합니다. |
| `lw ra, 8(sp)` | 스택에 저장해두었던 복귀 주소(`ra`)를 다시 읽어옵니다. |
| `addi sp, sp, 12` | 사용했던 스택 공간을 반환하기 위해 `sp`를 다시 12바이트만큼 올립니다. |
| `jalr x0, 0(ra)` | **복귀(Return)**: 원래 자신을 호출했던 지점으로 제어권을 넘깁니다. |

**2. 주요 단계 상세 설명**

*   **레지스터 복구 (Restoring registers)**: 함수 시작 지점인 **Slide 27**에서 `sw` 명령어로 대피시켰던 값들을 `lw`(Load Word) 명령어를 통해 다시 원래 레지스터로 채워 넣습니다. 이 과정을 통해 호출자($Caller$)는 자신의 레지스터 값이 함수 실행 전과 똑같다고 느끼게 됩니다.
*   **스택 정리 (Cleaning the stack)**: $sp$를 다시 원래의 높은 주소 위치로 올림으로써, 함수 실행 중에 임시로 확보했던 메모리 공간을 깨끗하게 반환합니다.
*   **최종 반환**: `jalr` 명령어가 실행되는 시점의 $ra$($x1$) 레지스터에는 스택에서 복구된 **"메인 프로그램으로 돌아갈 주소"**가 들어있습니다. 따라서 이 명령어를 통해 함수는 무사히 원래 자리로 되돌아갈 수 있습니다.

**요약하자면**, 에필로그는 남의 물건을 제자리에 돌려놓고 빌렸던 자리를 청소한 뒤 집으로 돌아가는 과정입니다. 이로써 삽입 정렬 함수의 전체 실행 과정이 완벽하게 마무리되었습니다.

### Slide 33: C Code to RISC-V Assembly (Summary)

이번 단원의 마지막 슬라이드는 우리가 지금까지 단계별로 분석했던 모든 어셈블리 코드를 한데 모아, 고수준 언어인 C 코드가 하드웨어 명령어인 RISC-V 어셈블리로 어떻게 최종 변환되는지를 요약하여 보여줍니다. 이는 `Compiler`(컴파일러)가 수행하는 핵심적인 역할을 시각화한 것입니다.

**1. 전체 구조 일람 (Overall Structure)**

| 단계 (Phase) | 코드 영역 (Code Section) | 주요 역할 (Key Role) |
| :--- | :--- | :--- |
| **준비 (Prologue)** | `Sort:` ~ `addi t2, x0, 1` | 스택 공간 확보, 레지스터 보존, 인자 설정 및 $i$ 초기화 |
| **외부 루프 (Outer)** | `Loop1:` ~ `lw t4, 0(s1)` | 루프 종료 조건 검사, $v[i]$ 주소 계산 및 `temp`($t4$) 로드 |
| **내부 루프 (Inner)** | `Loop2:` ~ `jal x0, Loop2` | $j$ 범위 및 값 비교, 데이터 오른쪽 이동, $j$ 감소 및 반복 |
| **삽입 및 순환** | `Loop3:` ~ `jal x0, Loop1` | 적절한 위치에 `temp` 삽입, $i$ 증가 및 외부 루프 반복 |
| **종료 (Epilogue)** | `Exit:` ~ `jalr x0, 0(ra)` | 레지스터 값 원상복구, 스택 포인터 정리, 호출 지점 복귀 |

**2. 컴파일 결과의 핵심 요약**

*   **효율적인 레지스터 활용**: 컴파일러는 자주 사용되는 인덱스($i, j$)와 배열 주소($v$), 그리고 임시 값($temp$)을 최대한 레지스터(`t` 및 `s` 레지스터)에 배치하여 메모리 접근 횟수를 줄였습니다.
*   **제어문의 구현**: C 언어의 `for` 루프와 `&&` 조건문이 `bge`, `blt`, `jal`과 같은 비교 및 점프 명령어로 정교하게 조립되었습니다.
*   **안전한 메모리 관리**: 함수 실행 전후로 스택을 조절함으로써, `Register Spilling`(레지스터 대피)과 복구가 완벽하게 대칭을 이루도록 설계되었습니다.

**결론적으로**, 이 한 장의 슬라이드는 소프트웨어의 논리가 하드웨어의 물리적인 동작으로 변환되는 전체 과정을 담고 있습니다. 고수준 언어의 추상적인 코드가 어떻게 구체적인 주소 계산과 레지스터 조작으로 바뀌는지 이해했다면, 이제 여러분은 컴퓨터 시스템의 가장 중요한 연결 고리를 파악한 것입니다.

# 대주제 3. 데이터 표현 및 주소 지정 방식 (Slide 34~43)

## 3.1 문자 데이터 표현 및 문자열 처리(strcpy) (Slide 34~40)

### Slide 34: Communicating with people & Wide immediate and address

우리는 지금까지 주로 정수(Integer) 데이터를 처리하고 정렬하는 과정을 살펴보았습니다. 하지만 컴퓨터는 숫자뿐만 아니라 인간과의 소통을 위해 '문자' 데이터를 처리해야 하며, 때로는 한 명령어의 크기를 넘어서는 매우 큰 숫자(상수)나 주소값을 다루어야 할 때도 있습니다. 이번 단원에서는 바로 이러한 데이터의 확장된 표현 방식과 주소 지정 기법을 학습합니다.

### Slide 35: Character Data

컴퓨터는 본질적으로 숫자만을 처리하는 기계입니다. 따라서 우리가 사용하는 알파벳이나 기호를 다루기 위해서는 각 문자를 특정 숫자에 매핑하는 약속이 필요합니다. 이번 장에서는 이러한 문자 인코딩 방식과 RISC-V 하드웨어가 이를 처리하는 방법을 학습합니다.

**1. 주요 문자 인코딩 체계**

| 종류 (Type) | 특징 (Characteristics) | 비고 |
| :--- | :--- | :--- |
| **`ASCII`** | 128개의 문자를 7비트로 표현 | 95개의 출력 가능한 문자 + 33개의 제어 문자 |
| **`Latin-1`** | 256개의 문자를 8비트(1바이트)로 표현 | ASCII에 96개의 서구권 그래픽 문자를 추가 |
| **`Unicode`** | 전 세계의 모든 언어와 기호를 수용하는 표준 | `UTF-8`, `UTF-16` 등 가변 길이 인코딩 사용 |

**2. 하드웨어 수준의 문자 처리**

대부분의 문자는 1바이트(8비트) 단위로 저장됩니다. 하지만 RISC-V의 기본 레지스터 크기는 64비트(혹은 32비트)이기 때문에, 워드($Word$) 단위가 아닌 바이트($Byte$) 단위로 데이터를 읽고 쓰기 위한 전용 명령어가 필요합니다.

*   **`lbu` (Load Byte Unsigned)**: 메모리에서 1바이트를 읽어 레지스터의 가장 오른쪽 8비트에 채우고, 나머지 56비트는 0으로 채웁니다(`Zero extension`). 문자는 보통 양수로 취급하므로 부호가 없는 `unsigned` 버전을 주로 사용합니다.
    *   예: `$lbu\ x12,\ 0(x10)$`
*   **`sb` (Store Byte)**: 레지스터의 가장 오른쪽 8비트(1바이트)만을 추출하여 메모리의 지정된 위치에 저장합니다.
    *   예: `$sb\ x12,\ 0(x11)$`

**요약하자면**, 컴퓨터는 `ASCII`나 `Unicode`라는 약속된 번호표를 통해 문자를 인식하며, RISC-V는 `$lbu$`와 `$sb$` 명령어를 통해 메모리에 저장된 바이트 단위의 문자 데이터를 효율적으로 조작합니다.

### Slide 36: Character Data – Cont'd (ASCII Table)
문자와 그에 대응하는 십진수 값을 정리한 `ASCII` 코드 표입니다. 예를 들어 공백(space)은 32, 대문자 'A'는 65, 소문자 'a'는 97로 정의되어 있습니다. 하드웨어는 이러한 수치 값을 통해 문자를 인식하고 처리합니다.

### Slide 37: Byte/Halfword/Word Operations

컴퓨터 시스템은 1바이트(`Byte`), 2바이트(`Halfword`), 4바이트(`Word`) 등 다양한 크기의 데이터를 다룹니다. RISC-V 레지스터는 기본적으로 64비트의 넓은 공간을 가지고 있지만, 메모리에서 이보다 작은 데이터를 가져올 때는 남는 공간을 어떻게 처리할지가 매우 중요합니다. 이번 장에서는 데이터 크기에 따른 로드 및 스토어 명령어의 차이를 상세히 비교해 보겠습니다.

**1. 데이터 크기별 명령어 요약**

| 데이터 단위 | 크기 (Size) | 로드 (Load) | 스토어 (Store) |
| :--- | :--- | :--- | :--- |
| **`Byte`** | 8 bits | `lb` / `lbu` | `sb` |
| **`Halfword`** | 16 bits | `lh` / `lhu` | `sh` |
| **`Word`** | 32 bits | `lw` / `lwu` | `sw` |

**2. 로드 시 확장(Extension) 방식의 차이**

메모리에서 읽어온 작은 데이터를 64비트 레지스터 $rd$에 채울 때, 두 가지 방식을 선택할 수 있습니다.
*   **부호 확장 (`Sign extend`)**: `lb`, `lh`, `lw` 명령어가 사용합니다. 데이터의 가장 왼쪽 비트(부호 비트)를 나머지 빈 공간에 똑같이 복사합니다. 음수 값을 유지해야 하는 정수 데이터를 다룰 때 적합합니다.
*   **제로 확장 (`Zero extend`)**: `lbu`, `lhu`, `lwu` 명령어가 사용합니다. 데이터의 크기와 상관없이 나머지 빈 공간을 모두 `0`으로 채웁니다. **문자 데이터**는 부호가 없는 양수로 취급하므로, ASCII 코드를 읽을 때는 주로 `$lbu$`를 사용합니다.

**3. 스토어 방식: 추출(Truncation)**

저장할 때는 로드와 달리 '확장' 개념이 필요 없습니다. `sb`, `sh`, `sw` 명령어는 레지스터에 담긴 64비트 데이터 중 오직 **가장 오른쪽(Rightmost)**의 8, 16, 32비트만을 골라내어 메모리의 지정된 주소에 저장합니다. 나머지 상위 비트들은 무시됩니다.

**요약하자면**, RISC-V는 다루려는 데이터의 크기에 따라 세분화된 명령어를 제공하며, 특히 메모리에서 레지스터로 데이터를 가져올 때 부호를 유지할지(`lb`) 아니면 단순히 0으로 채울지(`lbu`)를 프로그래머가 결정할 수 있게 설계되었습니다.

### Slide 38: Representation of string in C

앞서 개별 문자가 어떻게 숫자로 변환되는지 배웠다면, 이번 장에서는 여러 문자가 모인 `String`(문자열)이 C 언어에서 어떤 방식으로 메모리에 저장되는지 살펴보겠습니다. 문자열은 프로그램 내에서 이름이나 문장 등 가변적인 데이터를 처리할 때 사용됩니다.

**1. 문자열의 정의와 종료 조건**
*   **가변 길이**: 문자열은 정해진 크기가 없으며, 포함된 문자의 개수에 따라 길이가 달라집니다.
*   **종료 문자 (Null Terminator)**: 컴퓨터가 "문자열이 어디서 끝나는지"를 알 수 있도록, C 언어에서는 문자열의 맨 마지막 칸에 아스키 값이 $0$인 특수 문자를 추가하여 끝을 표시합니다. 이를 보통 `$'\0'$`라고 부릅니다.

**2. 예시 분석: "Cal"**
슬라이드에 나온 "Cal"이라는 문자열은 겉보기에는 3글자이지만, 실제 메모리에는 다음과 같이 **4바이트**의 데이터가 연속적으로 저장됩니다.

| 문자 (Character) | ASCII 값 (Decimal) | 메모리 위치 |
| :--- | :--- | :--- |
| **'C'** | $67$ | 첫 번째 바이트 |
| **'a'** | $97$ | 두 번째 바이트 |
| **'l'** | $108$ | 세 번째 바이트 |
| **종료 문자** | $0$ | 네 번째 바이트 |

**3. 주요 특징**
*   **연속된 배치**: 문자열의 각 글자들은 메모리 상에서 빈틈없이 나란히 배치됩니다. 따라서 우리는 첫 번째 글자의 주소만 알면, 주소값을 $1$씩 더해가며 문자열 전체를 읽을 수 있습니다.
*   **표 확인**: 하단의 아스키 표에서 빨간색 테두리로 표시된 $67$($C$), $97$($a$), $108$($l$) 값을 확인해 보십시오. 하드웨어는 이 숫자들을 순서대로 읽어 들여 "Cal"이라는 단어를 인식하게 됩니다.

**요약하자면**, C 언어에서 문자열은 문자들이 나열된 배열이며, 그 끝에는 반드시 **아스키 값 $0$**이 붙어 마침표 역할을 수행합니다. 이 구조를 이해해야만 문자열을 복사하거나 길이를 재는 프로그램을 올바르게 작성할 수 있습니다.

### Slide 39: String Copy Example

앞서 문자열이 메모리에 어떻게 저장되는지 원리를 배웠으므로, 이번 장에서는 실전 예제로 문자열을 다른 곳으로 복사하는 `strcpy` 함수의 C 언어 로직을 분석해 보겠습니다. 이 함수는 원본 문자열의 시작부터 종료 문자($0$)를 만날 때까지 한 글자씩 옮기는 작업을 수행합니다.

**1. C 코드 분석**

```c
void strcpy (char x[], char y[])
{ 
    size_t i;
    i = 0;
    while ((x[i] = y[i]) != '\0')
        i += 1;
}
```

*   **매개변수**: `char x[]`는 복사될 목적지 주소를, `char y[]`는 원본 문자열이 있는 소스 주소를 의미합니다.
*   **인덱스 초기화**: `i = 0`을 통해 문자열의 가장 첫 번째 글자부터 접근할 준비를 합니다.
*   **핵심 루프 조건**: `(x[i] = y[i]) != '\0'` 부분은 매우 효율적으로 작성되어 있습니다.
    1.  대입 연산: `y[i]`에 있는 문자 하나를 읽어 `x[i]`에 저장합니다.
    2.  비교 연산: 방금 복사된 그 문자가 `\0`(종료 문자, 아스키 값 0)인지 확인합니다.
    3.  종료 조건: 만약 복사된 문자가 0이 아니라면 인덱스 `i`를 1 키우고 루프를 반복합니다. 만약 0이라면 마지막 글자까지 복사가 완료된 것이므로 루프를 종료합니다.

**2. 하드웨어 관점에서의 특징**

*   **바이트 단위 접근**: 여기서 사용하는 데이터 타입은 `char`입니다. 정수($int$, 4바이트)와 달리 한 칸의 크기가 **1바이트**이므로, 하드웨어는 바이트 단위로 메모리에 접근해야 합니다.
*   **인덱스 증가**: 루프가 반복될 때마다 `i`가 1씩 증가합니다. 이는 메모리 주소를 1바이트씩 옆으로 옮겨가며 읽는다는 뜻입니다.

**요약하자면**, `strcpy`는 종료 문자($0$)가 나올 때까지 바이트 단위로 데이터를 읽고 쓰는 단순하지만 강력한 알고리즘입니다. 이제 이 추상적인 C 코드가 실제 RISC-V 하드웨어 명령어인 `$lbu$`와 `$sb$`를 사용하여 어떻게 구현되는지 살펴보겠습니다.

### Slide 40: String Copy Example – Cont’d (RISC-V Code)

이번 장에서는 **Slide 39**에서 분석한 `strcpy` 함수의 C 코드가 실제 RISC-V 어셈블리 명령어로 어떻게 구현되는지 한 줄씩 상세히 살펴보겠습니다. 이 예제는 문자 처리를 위한 바이트 단위 명령어(`lbu`, `sb`)와 루프 구조, 그리고 레지스터 보존 규약이 어떻게 결합되는지 보여주는 훌륭한 사례입니다.

**1. `strcpy` 어셈블리 코드 분석**

이 코드는 인덱스 변수 $i$를 위해 `Saved register`인 $x19$($s3$)를 사용한다고 가정합니다.

| 명령어 (Instruction) | 설명 (Description) |
| :--- | :--- |
| **`strcpy:`** | 함수의 시작 지점을 나타내는 라벨입니다. |
| `addi sp, sp, -4` | $x19$를 저장하기 위해 스택 공간 4바이트를 확보합니다. |
| `sw x19, 0(sp)` | 호출자가 쓰던 기존의 $x19$ 값을 스택에 보존합니다. |
| `add x19, x0, x0` | 인덱스 $i$를 0으로 초기화합니다 ($x19 = 0 + 0$). |
| **`L1:`** | 루프의 시작 지점입니다. |
| `add x5, x19, x11` | 원본 배열 주소 $y$($x11$)에 인덱스 $i$를 더해 $y[i]$의 주소를 계산합니다. |
| `lbu x6, 0(x5)` | $y[i]$로부터 **1바이트**를 읽어와 $x6$에 저장합니다. |
| `add x7, x19, x10` | 목적지 주소 $x$($x10$)에 $i$를 더해 $x[i]$의 주소를 계산합니다. |
| `sb x6, 0(x7)` | 읽어온 바이트($x6$)를 목적지 $x[i]$ 위치에 저장합니다. |
| `beq x6, x0, L2` | 방금 복사한 문자가 `0`(종료 문자)이라면 `L2`로 가서 루프를 끝냅니다. |
| `addi x19, x19, 1` | 인덱스 $i$를 1 증가시킵니다 ($i++$). |
| `jal x0, L1` | 다음 글자를 복사하기 위해 다시 `L1`으로 돌아갑니다. |
| **`L2:`** | 루프 종료 후 뒷정리를 하는 지점입니다. |
| `lw x19, 0(sp)` | 스택에서 $x19$의 원래 값을 읽어와 복구합니다. |
| `addi sp, sp, 4` | 사용한 스택 공간을 반환합니다. |
| `jalr x0, 0(x1)` | 호출자에게 제어권을 반환합니다. |

**2. 주요 특징 분석**

*   **오프셋 계산의 간소화**: 정수형 배열(4바이트)과 달리 문자열(1바이트)은 인덱스에 별도의 숫자를 곱할 필요가 없습니다. 인덱스 $i$ 자체가 곧 바이트 오프셋이 되므로 `add` 명령어만으로 주소 계산이 가능합니다.
*   **바이트 단위 조작**: 문자를 다루기 위해 워드 단위인 `lw`/`sw` 대신 바이트 단위인 `lbu`와 `sb`를 정확히 사용하고 있습니다.
*   **종료 조건의 활용**: C 코드의 `while` 조건문이 `beq`(Branch if Equal) 명령어를 통해 "0이 나올 때까지 반복"하는 로직으로 완벽히 구현되었습니다.

**요약하자면**, `strcpy` 어셈블리는 `lbu`로 읽고 `sb`로 쓰는 과정을 종료 문자($0$)가 나올 때까지 반복하는 구조입니다. 이 과정에서 $x19$라는 저장 레지스터를 사용했기 때문에 스택을 통한 보존 및 복구 과정이 포함되었습니다.

## 3.2 RISC-V 주소 지정 모드 및 프로그램 실행 준비 과정 (Slide 41~43)

명령어 세트 아키텍처(ISA)에서 데이터를 찾는 방법인 주소 지정 모드와, 이진수로 이루어진 기계어를 해석하는 과정, 그리고 소스 코드가 실행 가능한 상태가 되기까지의 전체 흐름을 정리합니다.

### Slide 41: RISC-V Addressing mode summary
RISC-V는 연산의 대상(피연산자)을 효율적으로 찾기 위해 네 가지 주요 주소 지정 방식을 사용합니다. 슬라이드 상단의 표는 `R-type`, `I-type`, `S-type` 등 각 형식의 비트 할당량을 요약하고 있습니다.

1.  `Immediate addressing`: 연산에 사용될 상수가 명령어 자체의 `immediate` 필드에 직접 포함되어 있는 방식입니다.
2.  `Register addressing`: 연산 대상이 레지스터 내부에 있으며, 명령어는 해당 레지스터 번호를 가리킵니다.
3.  `Base addressing`: `Base register` 값에 명령어에 포함된 오프셋($offset$)을 더해 메모리 주소를 결정합니다. `load/store` 명령어에서 사용됩니다.
4.  `PC-relative addressing`: 프로그램 카운터($PC$) 값에 명령어의 `immediate` 값을 더해 분기할 주소를 결정합니다. `beq`, `jal` 등 분기 명령어에서 사용됩니다.

### Slide 42: Decoding machine code
기계어 코드를 실제 어셈블리 명령어로 해석하는 `Decoding`(디코딩) 과정의 예시입니다.
*   **분석 사례**: `00578833_{hex}` 값을 이진수로 변환하여 필드를 나눕니다.
*   **해석 순서**:
    1.  가장 우측의 `Opcode`(0110011)를 확인하여 `R-type` 산술 명령어임을 파악합니다.
    2.  `Funct3`(000)과 `Funct7`(0000000) 필드를 조합하여 `add` 명령어임을 식별합니다.
    3.  `rs1`(01111 = 15), `rs2`(00101 = 5), `rd`(10000 = 16) 필드를 통해 레지스터 번호를 확인합니다.
*   **최종 결과**: 해당 기계어는 `add x16, x15, x5`로 해석됩니다. 우측의 표는 각 명령어 타입별 `Opcode`와 `Funct` 필드 값을 참조용으로 제공합니다.

### Slide 43: Translation and Startup
작성된 C 프로그램이 메모리에 로드되어 실행되기까지의 소프트웨어 도구 체인($Toolchain$) 과정입니다.
1.  `Compiler`: C 프로그램을 어셈블리어 프로그램으로 번역합니다. 최근의 많은 컴파일러는 직접 오브젝트 모듈을 생성하기도 합니다.
2.  `Assembler`: 어셈블리어 코드를 기계어 형태의 `Object module`로 변환합니다.
3.  `Linker`: 여러 개의 오브젝트 모듈과 라이브러리 루틴을 하나로 묶어 `Executable` 프로그램을 생성합니다. 이 과정을 `Static linking`이라고 합니다.
4.  `Loader`: 실행 파일을 보조 기억 장치에서 읽어 메인 `Memory`에 적재하고 실행을 시작합니다.
